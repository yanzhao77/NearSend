# 跨平台离线文件互传系统技术方案 V2.1

版本：V2.1　日期：2026-09-20　状态：产品方向与开发顺序已确认；技术能力及性能待真机验证

本方案将断点续传纳入首版核心能力，覆盖网络中断、手动暂停、进程退出和设备重启后的恢复。核心技术路线为 Flutter + 原生适配、Wi-Fi 数据传输、HTTPS 加密、二维码认证、分块校验和 SQLite 持久化。

## 产品摘要

| 项目 | 内容 |
|---|---|
| 产品名称 | 近传（NearSend） |
| 一句话定位 | 无需互联网，让手机与电脑安全、可靠地互传大文件，断线后还能继续。 |
| 首期平台 | Android、Windows；iOS 关键能力提前验证，后续完成正式集成 |
| 核心能力 | 离线组网、二维码配对、大文件传输、严格校验、持久化断点续传 |

### 核心用户旅程

1. 用户选择“发送”或“接收”，应用检查本地网络；没有路由器时引导 Android 创建离线热点。
2. 一台设备展示二维码，另一台设备扫码完成服务端身份校验和一次性配对。
3. 发送方选择文件；应用显示“正在准备文件”，完成分块、哈希和源文件可续传性检查。
4. 接收方确认文件清单、保存位置和完整空间需求后开始传输，并可暂停或在中断后恢复。
5. 应用完成整文件校验和最终保存，展示成功、失败及可重试文件，并提供打开保存位置的入口。

## 一、目标与范围

### 1. 产品目标

首要用户场景：无互联网环境下，手机与电脑可靠互传大文件。重点解决无可用互联网/路由器时建立连接，以及传输中断后保留已验证内容并继续的问题。“无网络”在本产品中指无互联网；实际传输仍需要建立本地 Wi-Fi 链路。

已确认的开发顺序：Android＋Windows 先形成内部可用闭环；iOS 的关键能力在 S0 提前验证，完整集成后完成三端正式版。首版保留严格校验，接受预扫描、恢复校验及可能的双份存储空间，不以省略完整性检查换取更短的演示时间。

产品差异与需求验证：小范围邀请目标用户实际完成无互联网连接、发送大文件、断开后恢复；记录操作失败点、总耗时、是否再次使用及现有工具不能满足的需求。当前定位已确认，不将未经试用验证的差异宣传为竞品缺陷。

开发 Android、Windows、iOS 双向文件互传工具。传输不依赖互联网、云服务器、账号系统或中转服务。在已有局域网内通信；没有路由器时优先由支持的 Android 设备建立本地热点。

首版正式发布包含：设备发现、二维码配对、文件与多文件队列、至少 20 GiB 单文件传输、加密、分块校验、整文件校验、持久化断点、暂停恢复、失败恢复、文件保存与记录。

### 2. 范围边界

- “离线”指设备之间存在可用的本地网络，但不需要互联网；不代表没有任何无线链路也能传输。
- 首版传输对象必须已在本地可读取。云盘占位文件需预先下载，离线时不能保证读取。
- 无线距离由设备与环境决定，不提供远程跨互联网传输。
- 首版不承诺 BLE 文件传输、目录同步、后台无限运行或任意 Windows 网卡自动开热点。
- iOS 首版以应用前台传输为保证条件；进入后台或被系统挂起时允许中断，返回后恢复。
- 重启后的续传需要重新启动应用、恢复源文件访问和网络连接；不保证应用在设备启动后自动运行。
- 未下载源文件、失效的文件授权、源文件改变、临时文件丢失、凭证被清除等情况需显式提示，不能假装续传成功。

### 3. 平台支持策略

Android 最低版本建议 Android 10；Windows 首版优先完成 Windows 11 验证，Windows 10 的具体版本列入兼容清单后再承诺；iOS 最低版本根据最终 Flutter 和插件组合冻结，发布前必须填写明确版本，不能使用“主流版本”作为验收条件。

## 二、连接场景与角色

### 1. 场景矩阵

| 环境 | 方案 | 支持边界 |
|---|---|---|
| 已有路由器，无互联网 | 两端加入同一可互通局域网 | 三端核心能力，需排除 AP 隔离和防火墙阻断 |
| Android + Windows，无路由器 | Android LocalOnlyHotspot，Windows 加入 | 首版发布前完成真机验证 |
| Android + iOS，无路由器 | Android LocalOnlyHotspot，iOS 加入 | 首版发布前完成真机验证 |
| Android + Android，无路由器 | 一端建立 LocalOnlyHotspot | 需权限授权及设备兼容测试 |
| Windows + iOS，无路由器 | Windows 可用热点或验证通过的 Wi-Fi Direct Legacy 路径 | 条件能力，不能作为所有电脑的基础保证 |
| Windows + Windows，无路由器 | 一端使用经验证的组网能力 | 条件能力 |
| iOS + iOS，无共同网络 | 用户建立可用个人热点后互传 | 若无可用热点，本方案首版不保证大文件互传 |

Android 官方明确 LocalOnlyHotspot 创建的网络没有互联网访问；权限还受 target SDK 和系统版本影响。[官方文档](https://developer.android.com/develop/connectivity/wifi/localonlyhotspot)

Windows 移动热点与 Wi-Fi Direct Legacy 是不同能力。后者允许非 Wi-Fi Direct 客户端接入，但两者不能同时运行。开发阶段必须在完全断开上游网络的条件下验证；不把“能打开热点设置页”等同于“能离线组网”。[微软文档](https://learn.microsoft.com/en-us/uwp/api/windows.devices.wifidirect.wifidirectlegacysettings?view=winrt-26100)

### 2. 三类独立角色

| 角色 | 取值 |
|---|---|
| 网络角色 | 热点创建者、热点加入者、普通局域网成员 |
| 文件角色 | 发送者、接收者 |
| 连接角色 | HTTPS 服务端、HTTPS 客户端 |

连接角色在同一任务的初次连接及后续恢复中固定，首版不支持跨角色恢复；原服务端不可用时等待其恢复。热点模式优先由热点创建者提供 HTTPS 服务；局域网模式由展示配对二维码的一方提供服务。

- 服务端是接收者：客户端通过 PUT 上传文件块。
- 服务端是发送者：客户端通过 GET 下载文件块，并报告接收方提交状态。
- 所有断点决定均由文件接收者的持久化记录作出，不由连接角色决定。
- 首版每个任务单向传输；反向发送建立独立任务，可复用已认证连接。

## 三、总体技术架构

| 层级 | 职责 |
|---|---|
| Flutter UI | 设备、文件选择、确认、进度、暂停恢复、保存结果 |
| 应用服务 | 任务编排、网络状态处理、错误恢复、用户决策 |
| 共享协议核心 | 配对、HTTPS 协议、分块、哈希、状态机、任务授权 |
| 持久化与存储 | SQLite、临时文件、源文件访问、最终导出 |
| 原生适配 | 热点、指定网络连接、平台权限、生命周期、安全凭证存储 |

首版优先验证 Dart 共享协议核心。是否采用原生 Socket 或 FFI，取决于 Android 网络绑定、移动端存储和 TLS 接口的原型结果；在技术验证阶段冻结，不允许三个平台各自实现不同协议。

计算哈希和大量磁盘操作移出 UI isolate。使用有界缓冲与背压，不能将整文件读入内存，也不能无限累积待写块。Platform Channel 主要传控制和状态；字节流跨原生边界时明确复制次数、块大小和内存上限，并用大文件实测。

选用 HTTPS/1.1 持久连接作为首版应用协议承载。HTTPS 运行于 TCP + TLS 之上，可离线使用；自定义任务、分块和续传协议不自动兼容 LocalSend。TLS 1.3 为首版目标，选定引擎必须完成三端验证；不支持时阻断并明确提示，不静默降级到明文。

## 四、发现与组网

### 1. 已有局域网

优先使用系统 mDNS/Bonjour，二维码直连作为必备备用入口。首版不强制同时开发自定义 UDP 组播，避免增加平台权限和重复发现复杂度。发现仅返回名称、临时设备 ID、协议版本、端口和能力，不能作为信任凭证。

同一 SSID 不保证可连接；连接探测需要区分：权限拒绝、网络隔离、服务未启动、防火墙阻断、端口不可达、证书不匹配。二维码只能绕过发现失败，不能绕过网络隔离。

### 2. Android 本地热点

1. 用户主动选择“创建离线连接”。
2. 原生插件申请所需权限并调用 LocalOnlyHotspot。
3. 等待热点就绪，获取系统提供的实际 SSID 与密码。
4. 枚举有效接口并启动监听，生成实际可用的连接信息；不得硬编码网关地址。
5. 展示二维码，由另一设备加入热点并连接服务。
6. 监听热点终止、网络丢失和地址变化事件。
7. 暂停任务默认保留连接及热点预约；完成任务后由连接页面提供“断开连接”。用户退出连接、主动断开或应用服务不再使用网络时，按资源引用计数释放热点预约。系统终止热点时转入等待重连，不能保证暂停期间系统一定保留网络。

另一台 Android 通过 WifiNetworkSpecifier 请求连接时处理系统确认，并把实际传输连接绑定到返回的 Network。不能依赖系统默认网络；手机可能同时保留蜂窝网络。[网络请求 API](https://developer.android.com/develop/connectivity/wifi/wifi-bootstrap)

### 3. Windows

已有局域网为基础能力。自动离线组网安排独立原型：分别验证移动热点和 Wi-Fi Direct Group Owner + Legacy 路径的可用性、权限、驱动和打包方式。通过设备能力检测决定是否展示“创建离线连接”。失败时提供 Android 开热点或使用已有局域网的指引。

防火墙配置限制到应用所需网络与访问范围；不关闭系统防火墙。使用稳定可配置监听端口、冲突时选择备用端口。随机端口不是安全措施。

### 4. iOS 与二维码

iOS 加入热点需通过受支持的系统流程及用户授权，保留手动连接指引。应用自定义二维码由本应用解析；不承诺系统相机一次扫码即可加入网络并完成配对。Windows 无摄像头时采用电脑展示、手机扫描。

第一阶段手动备用入口为“地址 + 完整配对信息”，不设计无法离线解析到设备地址的纯短码。后续短码方案需独立定义定位和认证机制。

BLE 仅在后续版本作为发现和辅助配对能力；不得通过未认证 BLE 通道直接发送热点密码、任务恢复密钥或把其传来的指纹当作可信身份。

## 五、安全配对与重启后的身份

### 1. 身份与凭证分层

| 信息 | 生命周期 | 用途 |
|---|---|---|
| 服务端身份私钥及证书 | 跨进程保存，可轮换 | TLS 身份与已配对指纹验证 |
| 一次性配对令牌 | 默认 5 分钟，成功后失效 | 首次客户端授权 |
| 会话访问令牌 | 当前认证会话 | 控制接口与文件操作 |
| 任务恢复密钥 | 未完成任务保留期内 | 重新建立任务授权 |
| 任务 ID / 文件 ID | 随任务保存 | 标识资源，不作为密码 |

身份私钥和恢复密钥使用平台安全存储或受其保护的加密持久化保存，不明文写入日志或普通 SQLite 字段。服务端保存恢复密钥的验证材料；发起恢复方保存可使用的凭证。

### 2. 首次认证

二维码包含版本、服务端身份指纹、候选地址、端口、会话 ID、高熵一次性令牌及过期提示。令牌至少 128 位随机熵；服务端以自己的有效期和使用状态为权威，不能依赖两台离线设备时钟完全同步。

客户端先建立 TLS 并校验二维码中的指纹，再在加密连接内提交配对令牌。证书校验必须限定在当前配对上下文，不能采用“接受所有不可信证书”的全局回调。TLS 库负责密钥协商，不自制 AES 或握手算法。

接收端显示发送设备、文件数、总大小、文件清单与保存位置，经用户确认后签发只覆盖当前任务和操作方向的权限。未知设备不能读取待发送文件、续传既有任务或写入目标目录。

### 3. 恢复认证

IP、SSID、端口可以改变，但任务 ID、内容清单和持久身份不能随普通重连改变。发现新地址后先验证原有服务端身份，再通过加密连接提交任务恢复凭证，获得新的会话令牌和写入世代。

身份证书轮换、设备重装或凭证丢失时要求重新扫码配对和用户授权。允许保留已有临时文件，经授权后重新关联任务；不能自动信任新指纹。恢复不会继续使用已过期的一次性配对令牌。

任务取消时立即撤销恢复授权；任务完成后撤销文件写入/读取授权，只保留受限的完成状态查询能力至完成后 7 天，用于处理最终回执丢失；到期返回状态已过期，不自动创建新任务或重新导出。

## 六、源文件准备与数据模型

### 1. 文件准备

首版默认采用预扫描：顺序读取源文件，同时计算每块 SHA-256 和整文件 SHA-256，界面显示“正在准备文件”。20 GiB 文件会增加一次完整读取，作为换取明确文件身份和局部修复能力的设计取舍。

推荐逻辑块 4 MiB，最后一块可较短；每个文件的块大小写入清单后不可改变。20 GiB 文件对应 5120 个完整块。整文件摘要是按原始文件字节顺序计算的 SHA-256，不是各块摘要拼接后的摘要。

源文件处理原则：

- 能获得稳定本地文件且支持定位时，保存可重新打开的引用和授权，不为续传强制复制所有大文件。
- 来源不支持稳定随机读取或重启后重开时，复制到应用持久暂存区形成可读取的副本；预先检查额外空间。
- 文件在准备或传输中可能被修改时，检查元数据变化，且每次发送的实际块都必须与预扫描块摘要一致。不匹配立即标记 SOURCE_CHANGED，禁止与旧任务内容混合。
- 需要保证严格的某一时刻快照时，必须使用可确保稳定性的快照/锁定来源；普通复制和检查时间戳不等价于原子快照。
- 源文件改变后建立新任务。内容完全相同且整文件身份验证通过时，允许用户重新选择源文件以恢复旧任务。

### 2. 协议清单示例

以下 ID 和摘要为占位值，真实实现使用完整随机 ID 和完整摘要。

```json
{
  "protocolVersion": 1,
  "transferId": "uuid",
  "manifestDigest": "sha256-of-canonical-manifest",
  "files": [
    {
      "fileId": "uuid",
      "relativePath": "Videos/demo.mp4",
      "sizeBytes": "21474836480",
      "chunkSizeBytes": 4194304,
      "chunkCount": 5120,
      "fileSha256": "full-file-sha256",
      "chunkManifestDigest": "sha256-of-ordered-chunk-list"
    }
  ]
}
```

线上的文件长度与字节偏移使用十进制字符串，内部使用经过范围检查的 64 位整数。块编号从 0 开始。定义固定版本的清单字段编码与摘要规范，不能直接对任意 JSON 文本做哈希。分块摘要清单分页传输、校验总数和总摘要后再冻结任务。

### 3. SQLite 权威记录

| 表 | 核心字段 |
|---|---|
| tasks | transfer_id、manifest_digest、peer_identity、方向、状态、保留期限、恢复凭证引用 |
| files | file_id、task_id、源引用/目标引用、size、chunk_size、file_sha256、临时路径、状态 |
| chunks | file_id、chunk_index、expected_sha256、length、committed 标志 |
| sessions | task_id、lease_epoch、checkpoint_seq、会话状态、过期时间 |
| exports | file_id、目标引用、导出状态、可恢复提交信息 |

断点只以接收方 SQLite 的已提交块状态为权威。不再并列维护可独立更新的 .resume.json。使用事务及明确的耐久性配置，例如经验证的 WAL + synchronous=FULL；数据库只能记录已完成数据同步的块。

## 七、断点续传核心设计

### 1. 续传粒度

首版按完整块恢复。块中途断开，该块重新传输；已经校验并持久化提交的其他块保留。resumeOffset 只是“从文件起点连续已提交的字节数”的派生值；存在局部损坏时，以缺失块区间为准，不能只依赖一个偏移。

### 2. 三种进度

| 进度 | 含义 | 可用于重启续传 |
|---|---|---|
| receivedBytes | 到达接收应用的数据 | 否 |
| writtenBytes | 写入调用成功的数据 | 不能单独作为保证 |
| committedBytes | 完整块校验通过、文件同步成功且断点事务已提交 | 是，恢复检查后使用 |

界面可以平滑显示传输进度，但恢复时只采信 committed 状态。用户看到少量进度回退时提示“正在重传未保存部分”。

### 3. 块接收与安全提交顺序

1. 验证任务授权、写入世代、块编号、预期长度和范围。
2. 按固定 offset 写入未提交块，计算实际 SHA-256。
3. 长度或摘要不符时不提交，并返回块错误。
4. 校验通过的块暂记为待提交，继续接受有界窗口内的数据。
5. 累计 16 MiB 或经过 1 秒触发一次 checkpoint；暂停、文件结尾和正常退出时也触发。
6. 等待对应写入完成并调用存储适配层的数据同步操作。
7. 同步成功后，在 SQLite 事务中标记这些块 committed 并递增 checkpoint_seq。
8. 数据库事务完成后才发布持久化确认。

接收写入队列按文件串行执行，checkpoint 与写操作按顺序隔离。文件同步失败、磁盘已满或数据库提交失败，都不得发送持久化成功确认。

HTTP 块请求可先返回“已校验、待提交”；此回复不等于断点确认。客户端通过独立控制连接获取 checkpoint 状态。首版最多保留约 16 MiB 未持久化数据，达到上限即背压，不等待每个 64 KiB 网络缓冲的应用确认。

### 4. 恢复流程

1. 加载未完成任务并显示“可继续”。
2. 检查源文件/临时文件和访问授权；恢复应用前台及必要网络。
3. 重新发现地址、验证身份、恢复任务授权。
4. 接收端作为唯一写入世代权威，在事务中创建新 lease_epoch，废止旧写入者；恢复请求携带幂等 request_id，同一请求重试返回同一结果。接收端为客户端时，由其本地事务分配世代并通过 /resume 告知服务端；服务端序列化更新会话映射，拒绝旧世代，不自行分配第二套世代。双方的恢复触发合并到同一任务恢复流程，单任务只允许一个恢复流程在途。
5. 暂停该文件写入，检查临时文件、数据库与清单的一致性。
6. 接收端返回缺失块区间、checkpoint_seq 和新 lease_epoch。
7. 发送端重新验证源内容，按缺失块顺序读取并发送。
8. 完成块校验、整文件校验和最终保存。

重新打开应用或设备重启后，首版采用保守恢复校验：流式复核已提交块的摘要，发现损坏只清除对应块提交状态。该过程会增加本地读取时间，界面显示“正在检查已接收内容”；这是本地校验，不是重新通过网络传输全部文件。

仅网络连接中断、进程仍运行且文件保持受控时，可以保留本进程的有效校验状态。任何异常恢复仍执行整文件终检。

### 5. 崩溃窗口处理

| 中断位置 | 恢复行为 |
|---|---|
| 正在接收某一块 | 此块未提交，重传 |
| 文件已写入，但尚未同步 | 不采信未提交数据，重传 |
| 文件已同步，数据库尚未提交 | 可覆盖重传未提交块，不误报完成 |
| 数据库已提交，确认尚未送达 | 查询接收方状态，保留已提交块 |
| 正在整文件校验 | 重新校验，无需默认重传全部文件 |
| 已完成重命名，任务状态未更新 | 核对实际文件、大小和哈希，恢复完成状态 |
| 完成状态已保存，最终回执丢失 | 状态查询返回已完成，不重复生成文件 |

硬件、文件系统或文档提供者不满足可靠同步语义时，不承诺断电后零数据丢失；恢复校验负责发现损坏并请求重传，最终校验通过前绝不宣称成功。

### 6. 示例

20 GiB 文件传到约 8 GiB 时断网，界面可能显示 8 GiB，但只有此前 checkpoint 提交的完整块属于安全断点。恢复后查询接收端缺失区间，重传未提交块并继续剩余约 12 GiB。不会从头重发整个文件。

若重启后发现早先第 100 块损坏，则缺失集合可以同时包含第 100 块和尚未传输的后续区间。已有正确块继续保留。

## 八、协议接口与幂等性

| 接口 | 含义 |
|---|---|
| POST /v1/pair | 消费一次性令牌并建立会话 |
| POST /v1/transfers | 提议任务及内容清单 |
| POST /v1/transfers/{id}/decision | 接收方接受或拒绝任务 |
| POST /v1/transfers/{id}/resume | 验证恢复凭证，协商新世代 |
| GET /v1/transfers/{id}/status | 获取任务状态、缺失区间、提交序号 |
| GET /v1/transfers/{id}/manifest | 分页获取冻结的文件与块清单 |
| PUT /v1/transfers/{id}/files/{fid}/chunks/{index} | 客户端向作为接收者的服务端上传块 |
| GET /v1/transfers/{id}/files/{fid}/chunks/{index} | 客户端从作为发送者的服务端下载块 |
| POST /v1/transfers/{id}/checkpoint | 客户端作为接收者时报告持久化状态 |
| POST /v1/transfers/{id}/pause | 请求暂停并提交安全进度 |
| POST /v1/transfers/{id}/complete | 发起终检/报告终检与保存结果 |
| POST /v1/transfers/{id}/cancel | 取消任务并撤销传输授权 |

所有任务接口在 TLS 内认证，按角色与任务授权限制。客户端作为接收者时，GET /status 的服务端副本只用于显示；恢复缺失集合由客户端本地接收记录经 /resume 提交并校验，不能以发送端缓存覆盖接收端事实。

恢复应答示例：

```json
{
  "transferId": "uuid",
  "fileId": "uuid",
  "leaseEpoch": "7",
  "checkpointSeq": "128",
  "state": "receiving",
  "committedBytes": "8589934592",
  "missingChunkRanges": [[2048, 5119]]
}
```

块区间为两端包含。实际接口按文件分页返回，限制单次响应长度。上传携带 lease_epoch、认证令牌及清单摘要；offset 由块编号和已冻结块大小推导，不能由对端任意指定写入位置。

幂等规则：同一个 transfer_id 对应不同 manifest_digest 时拒绝；同一块重复传输且内容一致时返回已有状态；与冻结哈希冲突时拒绝；旧世代请求不允许写入。任务状态变更携带请求 ID，超时后先查询结果再决定重试。

服务端发送文件时只允许读取被用户批准的 file_id 与块，不能提供任意路径下载接口。

## 九、校验、文件保存与路径安全

### 1. 校验流程

每个块使用清单中固定的 SHA-256 校验。全部块提交后，冻结写入并从磁盘流式读取整文件，比较文件长度和整文件 SHA-256。

若整文件校验失败，扫描块摘要定位损坏块并清除相应提交状态，重传后再次终检。若所有块摘要正确而整文件摘要不一致，视为清单或实现错误，不无限重传，返回 MANIFEST_INCONSISTENT。

块哈希需来自认证且冻结的清单。TLS 保护传输链路，哈希验证文件内容；二者不能替代身份授权。

### 2. 存储适配

StorageAdapter 至少暴露：openRead、readAt、writeAt、truncate、syncData、stat、reopen、commitLocal、export，以及 supportsSeek、supportsDurableSync、supportsAtomicCommit 等能力。

Android 文档选择器提供 URI，可能连接本地或云端文档提供者，不能一律转换为普通路径。[Android SAF 文档](https://developer.android.com/training/data-storage/shared/documents-files)

首版接收临时文件放在应用管理的持久目录中，不放可被系统随时清理的普通缓存目录。使用内部 file_id 命名，避免对端文件名参与临时路径构造。

完成后先提交应用内已验证文件，再导出到用户目标。仅在同一可控文件系统且支持该操作时使用原子重命名；跨文件系统、手机文档提供者采用独立导出流程，不能伪称原子操作。

导出可能需要第二份空间。UI 明确区分“接收完成”“校验完成”“保存完成”；导出失败可重试，不必重新传输。对无法证明导出提交结果的后端，重启后检查已有目标或请用户确认，不盲目新建重复文件。

### 3. 路径安全

拒绝绝对路径、盘符、UNC 路径、父目录跳转、NUL、Windows 备用数据流形式及不合法分隔符。处理 Windows 保留名、大小写和 Unicode 归一化冲突。首版不跟随符号链接或 reparse point；使用受控目录/句柄级操作防止检查与写入间的路径替换。

默认同名自动改名或请用户选择，不覆盖已有文件。首版提供多文件队列，递归目录传输待路径和冲突规则验证后启用；“目录同步”是后续独立功能。

## 十、状态机与用户体验

主流程：准备源文件、等待连接、等待接收确认、传输、校验、导出、完成。

| 状态 | 用户看到的动作 |
|---|---|
| PREPARING | 显示扫描/哈希进度，可取消 |
| WAITING_CONNECTION | 发现设备、扫码、创建或加入网络 |
| WAITING_ACCEPT | 等待对方确认文件 |
| TRANSFERRING | 显示速度、已接收/总量、暂停按钮 |
| PAUSED | 整个任务队列暂停，保留断点和可用连接，可继续或取消任务 |
| INTERRUPTED | 显示断开原因，满足条件后重试 |
| CHECKING_RESUME | 本地检查已保存块 |
| VERIFYING | 整文件校验进度 |
| EXPORTING | 保存到用户位置 |
| COMPLETED | 所有文件通过校验且所需保存完成 |
| PARTIALLY_COMPLETED | 队列处理结束，部分文件已保存，其余受阻或失败；可重试未完成项 |
| BLOCKED | 缺权限、缺空间、源变化等，等待用户处理 |
| CANCELLED / FAILED | 撤销权限，提供保留或清理说明 |

网络可恢复错误采用 1、2、4、8 秒递增并加随机抖动，最大 30 秒；前台自动尝试约 2 分钟后转为等待用户，不无限唤醒设备。重连必须重新认证。

默认未完成任务保留 7 天，展示空间占用并允许延长或清理；传输活动中不按过期时间删除。暂停作用于整个任务队列：停止调度新块，等待在途块完成或安全中止，强制 checkpoint 完成后才显示 PAUSED；暂停完成后无持续文件写入。取消撤销授权并默认清理尚未完成的应用内临时数据，已导出文件保留。删除已保存文件必须是独立明确操作，不能随取消任务发生。删除文件的动作必须与按钮文案一致。

接收已确认任务的相同清单可恢复；文件数量、内容清单、目标位置或身份发生变化时重新请求确认。

## 十一、平台实现分工

| 平台 | 原生职责 |
|---|---|
| Android / Kotlin | 热点、WifiNetworkSpecifier、网络绑定、网络监听、文件 URI、权限、前台服务、安全凭证 |
| iOS / Swift | Bonjour、本地网络授权、热点加入请求、文件访问生命周期、安全凭证、前后台状态 |
| Windows / C++ WinRT | 接口枚举、热点/Legacy 能力验证、防火墙引导、文件操作、安全凭证、托盘 |

Android 后台方案需依据实际用途选择合适的前台服务类型并处理系统限制，不能将“前台服务”视为无限运行保证。[Android 前台服务文档](https://developer.android.com/develop/background-work/services/fgs/service-types)

热点预约和传输引擎的生命周期应由应用服务管理，不能只挂在一个 Flutter 页面上。页面关闭不应意外释放正在使用的网络；进程终止则依靠持久化恢复。

iOS 不通过播放静音、伪装后台用途等方式维持传输；用户离开应用后若系统挂起，回到前台从安全断点继续。

## 十六、产品体验与空间管理要求

### 1. 准备、恢复和完成的用户表达

- 准备阶段：“正在准备文件：已扫描 X / Y。准备完成后开始传输。”展示读取/哈希进度，可取消；仅在能可靠估计时显示剩余时间。文件很多时同时显示已处理数量。
- 恢复校验：“正在检查已接收内容，检查通过的部分无需重新传输。”显示本地检查进度；完成后再显示缺失数据传输进度。
- 接收前确认文件数、总大小、目标位置、暂存占用及预计额外空间。存储提供者无法查询剩余空间时显示“无法确认可用空间”，由用户确认后尝试，并持续处理写入失败，不能标记为检查通过。
- 任务状态依次区分准备、连接、等待确认、传输、校验、保存和完成。传输速度只反映网络阶段；端到端总耗时单独记录。
- 部分文件失败后继续其他可处理文件；身份异常、清单级不一致等任务级错误暂停整个队列。空间不足时仅继续能够证明空间足够的文件，否则阻断。重试只处理未完成项，不重传已保存项。

### 2. 空间计算

按实际存储卷/提供者分别核算。新增空间需求 = 尚未分配的暂存空间 + 导出峰值额外占用 + 源文件必须暂存时的新增占用 + 数据库及安全余量。同一卷的并存需求相加，不同卷分别检查；已有实际分配的临时文件空间不重复扣减，稀疏文件的逻辑长度不能视为已实际分配。

首版按保守峰值检查。20 GiB 文件在暂存与完整导出副本并存时可能需要接近 40 GiB 文件空间，另加余量；同卷原子提交等已验证路径可降低估算。初始安全余量取每卷 max(256 MiB, 预计新增文件占用的 1%)，属于可调整策略，不是空间足够的保证。其他应用可能继续占用空间，因此每个文件开始及导出前重新检查，写入失败仍需保留可恢复状态。

应用内已验证副本在成功导出及提交结果可确认后释放，除非用户明确选择保留。未完成任务空间可查看、延长保留或清理。取消任务不删除已经导出的用户文件。

### 3. 文件来源

Android SAF URI 通过适配层访问，不强转真实路径；区分本地可定位、无法稳定定位、授权失效、未下载的云端文件。必要暂存前解释耗时和空间；离线无法读取云端内容时提示先下载，不无限重试。iOS 及 Windows 同样按来源能力判断，不能由扩展名推断可续传性。

### 4. 页面与连接动作

首页提供发送、接收、继续任务；连接页提供同网发现、创建离线连接、扫码及手动指引；确认页展示清单与空间；任务页覆盖所有阶段；结果页提供打开位置与失败重试；空间页管理未完成任务。

Windows 无摄像头时由电脑展示配对码、手机扫描，电脑担任服务端；文件发送方向仍可双向。Android 热点且手机担任服务端、电脑无法扫码时，首版使用地址＋完整配对信息的手动备用入口，不假设一个离线短码能定位和认证设备。该路径必须真人试用；如操作复杂，后续独立设计已认证的引导方式。二维码不能消除加入网络所需的系统确认。

## 十七、协议冻结、版本管理与发布门槛

### 1. 协议实现前必须冻结的细节

T02 交付字段类型、必填/可选及缺省规则、未知字段处理、UTF-8 编码与清单规范化算法、摘要覆盖范围、分页顺序和边界、错误码、超时和重试语义。提供固定测试向量覆盖空文件、尾块、超过 4 GiB 偏移、Unicode 文件名、字段顺序变化、重复/缺失块及非法输入。算法选定后写入协议版本，不让各平台自行选择。

首次能力协商交换协议主/次版本与所需能力。主版本不一致拒绝；次版本仅在双方共有能力覆盖任务需求时继续。更新客户端不得自动修改既有任务的冻结清单、块大小或摘要规则。v1 角色恢复固定，接收者是唯一断点与世代权威。

任务级恢复按 task_id 串行，创建/暂停/恢复/完成/取消均有幂等 request_id 和状态迁移规则。完成后状态查询凭证与文件读写授权分离。7 天完成查询期结束后不能仅凭旧请求自动重复创建文件。

### 2. 项目材料与 AI 工作约定

项目保留需求验收说明、架构/协议说明、任务清单、AI 项目规则、运行发布说明，可以按规模合并。关键决定进入 Git，不只保存在聊天记录中。每次开发读取相关材料；复杂改动先给计划，小功能直接实现并验证。

AI 完成任务时提供修改概述、实际执行的测试及结果、未执行原因和剩余风险。禁止通过删除失败测试、关闭证书校验、吞掉异常或显示假完成来通过验收。重点人工复核安全配对、文件写入、checkpoint、迁移和删除路径。每个验收通过的任务提交 Git，保留已知可用版本。

### 3. 安装、升级和诊断

构建可复现，依赖锁定，签名/密钥与源码分离。记录安装包版本、协议版本、数据库 schema 版本和构建提交。升级迁移前采取适合 SQLite 的一致性备份策略，不能在 WAL 活跃时只复制主数据库；失败保留旧数据并停止写入。降级客户端遇到更高 schema 时拒绝打开写入，不能强行修改。

日志覆盖阶段、错误码、checkpoint 序号、性能计数和版本；不记录令牌、恢复密钥、私钥或完整敏感清单。诊断导出由用户主动触发并可预览。不需要账号、云端日志或联网分析即可完成核心功能。

### 4. 平台发布与更新策略

| 平台 | 内测渠道 | 正式发布渠道 | 更新机制 |
|---|---|---|---|
| Android | 签名 APK，通过 GitHub Releases 或受控下载地址分发 | Google Play；在不具备商店条件的地区保留官网/Release APK | Google Play 使用商店更新；直接安装版只检查已签名的版本清单，由用户确认后下载和安装，不静默安装 |
| iOS | TestFlight | Apple App Store | TestFlight/App Store 更新；遵守系统后台与本地网络权限要求，不实现绕过商店签名的自更新 |
| Windows | MSIX 测试包或签名安装包 | 优先 MSIX；同时提供签名的直接下载包 | MSIX 使用受信任更新源；直接下载版检查签名版本清单并提示用户安装，不以应用自身权限静默替换可执行文件 |

发布产物必须来自可复现的 CI 构建，并记录应用版本、协议版本、数据库 schema 版本、Git 提交和签名身份。正式版与测试版使用不同发布通道；不得在仓库、日志或安装包资源中保存签名私钥、证书密码、商店密钥或更新服务凭证。

更新策略遵循兼容性优先：先完成数据迁移和协议能力协商，再启用新功能。涉及协议主版本、数据库 schema 或凭证存储的升级必须提供迁移测试与失败回滚路径。客户端只在有互联网时检查更新；无互联网不影响发现、配对、传输、恢复、校验和保存等核心功能。强制更新只能用于已经确认无法安全兼容的版本，并必须解释原因，不能让一般版本提示阻断离线传输。

每个平台发布前检查签名、权限声明、隐私说明、安装/升级/卸载、旧任务迁移及离线启动。GitHub Releases 中同时发布版本说明和 SHA-256 摘要；正式渠道包必须与对应 Git 标签及 CI 产物可追溯关联。

### 5. 发布与反馈

先在固定设备矩阵完成技术和故障验收，再进行小范围真人试用。发布阻断项：内容损坏、假完成、越权访问、错误删除、无法恢复的迁移、所承诺模式无法连接。所有性能数据附机型、系统、频段、距离、来源/目标存储和各阶段时间。

试用记录连接成功率、核心任务完成率、中断恢复结果、准备/恢复/导出耗时、操作步骤和用户是否再次使用；小样本展示次数和条件，不宣传为普遍成功率。若需要联网收集反馈，另行取得用户同意；默认可用本地记录及用户自愿反馈。
