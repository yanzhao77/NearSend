## 目标

让「用户扫码 → 确认对端身份 → 才交出一把只能消费一次的令牌」这条链路有一个
**不依赖调用方纪律**的实现：令牌在指纹比对成功之前**取不到**，而不是「文档说不要提前发」。

同时把 QR 载荷的解析做成严格解析：它是客户端从不受信来源读到的第一个东西，
并且决定「连到哪里」和「信任谁」。

## 范围内

- **配对载荷（§3/§4）**：`kind`、协议版本、`serverFingerprint`、`sessionId`、
  `candidates`（≤8，`host` 必须是裸地址、`port` 1–65535）、`pairToken`（base64url 无填充 32 字节）、
  `expiresInSeconds`；UTF-8 ≤ 4096 字节；**未定义字段一律拒绝**（§4）。
- **base64url 规范编码（§4）**：无填充、URL 字母表、**解码后重新编码必须相同**。
- **指纹计算（§2）**：`SHA-256(叶证书完整 DER)` 小写 64 hex。
  **不是** PEM 文本摘要，**不是** SPKI 摘要。
- **每连接信任上下文（§2）**：比对成功前不得释放令牌；比对失败关闭连接且不得复用；
  未使用前 `abandon()` 可关闭。
- **安全负例**：错误指纹、大写指纹、非规范 base64url、带 scheme/凭证/路径/查询的 host、
  保留字段、超限载荷等。

## 接口与不变量

- **令牌在比对成功之前取不到。** 这不是文档约定：`PairingHandshake` 只通过一个 getter
  暴露令牌，且该 getter 在未比对或已关闭时抛 `PAIR_REJECTED`。调用方没有「顺序」需要记住。
- **比对失败即关闭连接**（§2），且**不得在同一上下文上重新协商**——
  在对端身份校验已失败的连接上重试，正是重试循环变成攻击的方式。
- **每连接隔离**：一个连接的失败不泄漏到另一个连接。
- **不够用的证书编码也关闭连接**：不变量是「除非比对显式返回 trusted，否则关闭」。
- **指纹按 DER 计算**：参数类型是字节而非字符串，因此没有「传 PEM」的重载。
- **比较不是常数时间**：指纹发布在用户扫描的二维码里，不是秘密，时序信道不泄漏任何
  攻击者尚未拥有的东西；手写常数时间比较等于为不存在的问题发明密码学代码（`AGENTS.md` §5）。
- **候选地址选择不得绕过 pin**（§3）：本任务只做词法校验，可达性判定属 B02。

### `t03-01-02`：配对令牌生命周期与 `/v1/pair` 模型

已实现 `pairing_token.dart`、`pair_request.dart` 与 60 项测试
（Flutter 测试总数 426 → 486；安全层测试 68 → 128）。
详见[运行汇总](../testing/evidence/2026-09-20/t03-01-02/summary.md)。

**令牌生命周期**：300 秒窗口以**单调计时**判定（墙上时钟可被 NTP 或用户改时间移动，
那会延长令牌寿命或让活令牌立刻过期）；单次消费；**服务重启失效是构造性的**——
不持久化任何令牌状态，所以没有「可能被漏掉的失效步骤」；响应丢失后没有任何 API 能恢复令牌。

**只保存摘要**：§2 已为恢复密钥确立「服务端仅保存验证摘要」，配对令牌同样处理。
**诚实标注**：这一条**没有测试覆盖**（Flutter 无 `dart:mirrors`，无法断言内部字段），
由代码结构保证，已在运行汇总里明确写成「未经测试」而不是含糊带过。

**比较不声称常数时间，并说明原因**：Dart 不提供时序保证（JIT 可重排），
手写「常数时间」循环会是一种**虚假保证**。真正约束风险的是 256 位熵、单次消费、
300 秒窗口、滑动限流与「只比较摘要」。

**统一失败做成结构性**：`PairingRejection` 只用于本地诊断，
而 `wireCode` 对三种拒绝原因是**同一个常量**，测试断言这一点，并断言本地理由从线上答案不可达。

**限流在令牌之前检查**：已被限流的调用方即使拿的是**正确**令牌也只得 `RATE_LIMITED`，
因此无法靠「换令牌再试」探测哪个令牌存在（有测试覆盖）。

**capability 词表不发明**：复用 T02-02 的 `CapabilitySet`，测试全程用合成标识符。

**期间发现一个协议内在张力（已登记，未修）**：§9 要求 `requestId` 幂等重放，
但 §3 要求配对响应丢失后**不恢复**已消费令牌——配对是 §9 幂等的一个例外。
本层只校验 `requestId` 格式，**没有**实现任何幂等重放语义，因为对配对而言重放正是 §3 禁止的事。

### `t03-01-03`：`/v1` 线上契约层

已实现 `json_body.dart`、`wire_error.dart` 与 79 项测试
（Flutter 测试总数 486 → 565；协议层测试 124 → 204）。
详见[运行汇总](../testing/evidence/2026-09-20/t03-01-03/summary.md)。

**控制体不能只交给 `jsonDecode`**：Dart 的解码器**不拒绝重复的对象键**（保留最后一个、什么也不说），
这正是解析器差分的形状——两个实现读同一批字节、得出不同的值。
所以先扫描一次结构（深度、重复键、转义）再取值；扫描器**刻意不构建值**，
因为两个都构建的解析器就是两次产生分歧的机会。

**重复键可以藏在转义里**：`{"a":1,"\u0061":2}` 是同一个键的两种拼写。
比较原始文本会判为合法，所以扫描器**先解码转义再比较**（含代理对）。
另外，重复键的**报错不回显键名**——键来自请求体，而控制体可以携带令牌。

**错误体的 `message` 不是自由文本**：`WireError.of(code)` 不接受 message 参数，
只写入该码的 `messageKey`（封闭常量集），所以调用方传什么都到不了这个字段。
这把 T02-02 那句注释（"A key rather than a string: §7 requires the message to carry no secret"）
变成了结构。**收到的** message 不同：对端可发任意文本，只限长并查控制字符，
**不**猜测它是否含密钥（那种启发式只会带来虚假的安心）。

**`retryable` 是校验而非采信**：一个发来 `retryable: true` + `CHUNK_HASH_MISMATCH` 的对端
等于邀请客户端**永远重试一个损坏的块**，所以解析值必须与 §11 的行为一致，两个方向都测。

**§11 的表被双向钉住**：表中每个码的状态必须一致，且枚举里不能有表中未出现的码。

**`Retry-After`**：只接受 delta-seconds，**拒绝 HTTP-date**（离线时钟正是协议别处拒绝信任的东西）；
429 必须带正数延迟；限流器新增 `retryAfterSeconds`，从**最早的失败**何时移出窗口推导，
而不是窗口长度——在 20 秒就够的时候让客户端等满一分钟是另一种错。

### `t03-01-05`：清单分页与 seal

已实现 `manifest_page.dart`、`manifest_staging.dart` 与 50 项测试
（Flutter 测试总数 603 → 653；协议层 241 → 292）。
详见[运行汇总](../testing/evidence/2026-09-20/t03-01-05/summary.md)。

**页结构是 sealed 类型**：§6 规定 files 页不得带 fileId、chunks 页必须带，且两种页的 items 是不同记录。
用一个类加可选字段就允许两种被禁止的组合；sealed 让类型本身拒绝它们。
页内**索引不是自由的**：「每页覆盖连续索引区间」意味着第 i 项索引必须等于 `startIndex + i`。

**字节上限靠编码测量而非估算**：估算要同时把 JSON 转义、十进制字符串字段与多字节字符都建模对；
把候选页真的编码出来量一次，在这些方面都无法出错。
**一个诚实的发现**：按 §5.1 的 1024 字节路径上限，现实输入下**条目上限总是先起作用**，
字节上限是安全网——测试用最大合法路径填满 128 项断言一页装得下，
另用发送方不可能构造出的超大条目驱动机制本身。

**重传由内容决定，而不是由区间决定**：§6 拒绝的是「重叠区间**内容不一致**」，
把规则写成「拒绝重叠区间」会拒绝只是换了边界的诚实重传。
**按索引存储是让「不能用重复页增加累计数量」成立的结构**——
append 到列表的实现能通过天真的重传测试，却仍会把重复页算两次（有测试断言三次发送后计数不变）。
乱序到达也能正确 seal，因为页的 `startIndex` 就是承载 §5 逻辑顺序的东西。

**seal 按 §6 的顺序检查，摘要放最后**：摘要对每一种问题都会失败，却对「是哪一种」一言不发，
所以先报「file index 1 is missing」。摘要检查复用 T02-01 的 `FrozenManifest.verifyDigest`
（其注释里当初就写了「§6 seal」）；块长度检查复用 `chunkLengthForIndex`，
使对端**不能**靠声明短块跳过字节。

**30 分钟窗口只回答问题，不执行清理**：`isExpired` 是谓词；清理动作属于拥有那些状态的服务端。
窗口从**首次内容**起算，否则一个还没开始上传的提议会在客户端仍在决定时过期。

### `t03-01-07`：§8 请求头与体规则

已实现 `chunk_headers.dart` 与 40 项测试（Flutter 测试总数 702 → 742；协议层 341 → 381），
并修正一处跨层的错误码缺陷（见下）。详见[运行汇总](../testing/evidence/2026-09-20/t03-01-07/summary.md)。

**为什么做成纯函数**：§8 的这些是**帧定界规则**，而请求走私就住在帧定界里。
放进「对收到时的头映射求值的纯函数」，判定与「读 body」彻底分离
（**帧不合法的消息一个字节都不会被处理**），且**不需要 socket 就能完整测试**。

**「单一 Content-Length」在头映射里意味着什么**：头映射无法把同名放两次，
所以重复会以两种形态出现，**两种都拒绝**——只差大小写的两个条目
（HTTP 字段名大小写不敏感，**悄悄合并就会替实现选一个长度**），
以及逗号连接的一个值（那是对端在**说存在两个长度**）。

**只有本项目自己的命名空间被拒绝**：HTTP 带着大量无关头，全部拒绝是错的；
但 `X-LFT-` 前缀是我们自己的，那里的未定义头被拒绝（理由同 §4 拒绝未定义 JSON 字段）。

**冻结清单是权威**：`agreesWithManifest` 报告对端的摘要是否与清单一致，
**但不把不一致变成拒绝**——在参考性字段上拒绝，等于把一个对端本来影响不了的失败权交给它。

**期间发现并修正一个真实缺陷**：§8 要求内容冲突返回 `CHUNK_HASH_MISMATCH`，
并说「不可因『已有块』就无条件成功」。追查后确认**校验本身是有的**
（与**冻结清单**比对，权威来源正确），**但错误码是错的**：
`syncReceiptMismatch` 当时**没有线路码映射**，于是 `toProtocolError()` 的兜底分支
把它报成 **`DB_COMMIT_FAILED`（500，可重试）**——**邀请客户端无限重发一个内容冲突的块**，
正是 §8 与 §11 各自禁止的事。已映射为 `CHUNK_HASH_MISMATCH`（422，不可重试）并补测试。
这个缺陷是**把 §8 的文字与存储层实际行为对照**才发现的：两边测试各自都是绿的。

### `t03-01-08`：§8 批量 checkpoint 窗口与 `checkpointSeq`

已实现 `commit_window.dart`、schema v3（`tasks.checkpoint_seq`）与存储层的批量提交路径
（Flutter 测试总数 742 → 782；窗口 23 项 + 存储 14 项 + 迁移 3 项）。
详见[运行汇总](../testing/evidence/2026-09-20/t03-01-08/summary.md)。

**为什么需要窗口**：§8 允许用 `verified_pending` 而不是 `committed` 回答块 `PUT`，
因为字节已落盘并验证但**没有任何块行被提交**，断点没有前进。这是有意的取舍——
每块单独提交是每 4 MiB 一个事务，批量提交的代价是崩溃时丢掉上次 checkpoint 之后的工作。
§8 用两道界限框住损失（**16 MiB**、**1 秒**）并在**暂停/文件结尾**强制提交。

**窗口里有意的「没有」**：**没有第三种块状态**。`chunks.state` 仍是 `missing`/`committed`，
因为「已写但未提交」不是进度（`AGENTS.md` §2 规则 5），
一个 `verifying` 状态会成为「我们到哪了」的第二个答案。`verified_pending` 是**响应**而非存储状态，
所以窗口中途崩溃会把块留在 `missing`，它们只是被重传——测试直接钉住这一点。

**窗口持有「收据」而非索引**：批量提交在**事务内**把每张收据与冻结清单再比对一次。
只记索引会让批量提交变成一条「把任何已登记块标成已提交而无需证据」的路径。
摘要冲突使**整批**失败、一条都不提交、序号不前进（半应用的 checkpoint 会谎报进度）。

**「单一提交路径」被保留而不是被并列**：`commitChunkAfterSync` 现在**是**
`CommitWindowPolicy.immediate`（容量=一个块、间隔=0）下的同一个窗口路径，
所以标记 `state='committed'` 的 SQL **只有一处**。立即策略必须用**零间隔**表达——
尾块小于一个块，只靠容量判断它永不到期，于是每个文件的最后一块都会停在 `verified_pending`。

**`checkpointSeq` 落在 `tasks`**：它的搭档 `lease_epoch` 在那里，而 V2.1 把
`checkpoint_seq` 放在本仓库并不存在的 `sessions` 表里；该偏离已登记。
**作用域选每任务**（§8 未点名），理由同上。v3 用 `ADD COLUMN ... NOT NULL DEFAULT 0`，
`applyVersion1`/`applyVersion2` 一字未改，并再次自动验证「新库与升级库的列完全一致」。

### `t03-01-09`：§8 写入栅栏（每文件串行 + 恢复交接）

已实现 `write_fence.dart` 与 21 项测试（Flutter 测试总数 782 → 803），
并把栅栏接到仓库上（`writeChunkWithFileLock`、`revokeAndAdvanceLeaseAfterWritesStop`）。
详见[运行汇总](../testing/evidence/2026-09-20/t03-01-09/summary.md)。

**已有的世代检查为什么不够**：存储层已能在提交事务内再查一次世代，让被取代的写入
**无法提交**——但没让它无法**写入**。缺的两个都关于时间：
（1）没有东西把同一文件的两个写入者串行化，两者的字节会交错写进同一个暂存文件，
而输的一方在提交被拒时**字节早已落盘**——**已提交的块行仍然是对的**，这正是危险处；
（2）`revokeAndAdvanceLease` 只递增世代不等待，一个正在 sync 中途的写入会继续写进
新一代即将使用的文件。

**顺序即保证**：先**拒绝**旧世代的后续写入（立即），再**等待**它的写入者全部停止，
然后才分配新世代。若只在世代变化时才拒绝，等待期间会冒出新的旧世代写入，等待永不结束。
排队的写入也在拿到文件槽**之前**就登记，故 drain 也等它；
而拿到槽之后**再查一次**世代，不通过就一个字节都不写——这一步是必需的，
因为一个写入可能先通过检查、排在别人后面，等排到队首时恢复已经接管。

**在途写入被允许写完并提交**：中止它只留下半写的暂存文件而无好处，
而 §8 下一步「**校验已有数据**」正是让旧世代下提交的块可以保留的原因。
栅栏保证写入**停止**，不保证它**被撤销**。

**超时不得被读成「写入已停止」**：`timeout` 到期**抛错**且**不分配**世代，
世代保持被撤销以便重试——把超时当「停了」的调用方会在旧写入仍在写文件时分配新世代。

**没有重复上一批的「孤儿模块」问题**：仓库**持有**栅栏（各造一个栅栏等于没有栅栏），
`writeChunkWithFileLock` 是「写入顺序 + 文件锁」的一次调用，
`revokeAndAdvanceLeaseAfterWritesStop` 把三步做成一次调用。

**用变异验证测试不是空的**：三处临时变异分别导致 **4 / 3 / 1** 项失败
（去掉串行化、drain 永不等待、去掉二次检查），随后恢复原文并重新确认全部通过。
