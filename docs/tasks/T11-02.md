## 1. 目标

把已经存在、已经被测试、**但还没有被任何入口调用的三样东西接起来**：

1. `NearSendNode`（真实节点：数据库、身份、端点、TLS 服务器）；
2. `TransferClient`（已配对的连接）；
3. `SendingSession` / `TransferEngine` 的接收侧方法。

接起来的判据不是「界面能点」，而是：**用户从首页选文件、确认、点「发送」，字节真的到达对端磁盘并校验通过**。

## 2. 现状（本卡存在的理由）

- 首页两个按钮**已接真实路由**；连接页、传输详情页、接收确认页、文件选择结果页、进度模型、
  协议状态→阶段映射、SAF 通道与选择控制器**都已完成并有测试**。
- `SendingSession` 已被一条**真实 TLS 测试**证明能把「选择的文档」变成「接收端磁盘上的同哈希文件」。
- **但应用从不启动节点**：`lib/app/` 里没有 `NearSendNode` 的任何引用，因此文件选择页拿不到
  `SendingSession`，「发送」按钮**没有可调用的东西**。这不是 UI 缺页面，而是缺生命周期。

## 3. 范围

本卡**必须**完成：

1. **节点生命周期**：应用启动时在应用私有目录打开 `NearSendNode` 并持有它；退出时 `stop()` + `close()`。
   身份**必须先想清楚是否需要持久化**：当前 `NearSendNode.open` 每次都生成新 TLS 身份，
   而 T03-02 的残余项正是「身份尚未持久化」。**若本卡不持久化身份，就必须在 UI 明说每次启动 pin 会变**，
   不得让用户以为配对可以跨重启保留。
2. **身份与配对状态**：把「本机连接信息」（pin、候选地址、会话）从真实节点喂给 `ConnectionPage`
   （该页已接受 `PairingPayload?` 并在为 null 时明说），把粘贴的载荷交给 `pairFrom`。
3. **选择 → 会话**：`FileSelectionController.choicesFor`（`t11-01-16`）产出的 choices 交给
   `SendingSession.plan` → `propose` → `openWriteGeneration` → `sendFile`。
4. **实时进度**：`SendingSession.sendFile` 的 `onProgress` 驱动 `TransferProgress`；
   **已传字节必须是「对端已确认的块」**（§9：接收端的行才是进度权威，发送端只持镜像），
   阶段必须来自 `phaseForTransferState`（`t11-01-15`）而不是另写一套词。
5. **接收侧**：作为 `client_to_server` 的接收方，用 `acceptLocally` + `finishFile`；
   作为 `server_to_client` 的接收方，用 `registerRemoteManifest`/`registerRemoteFile` +
   `adoptLeaseEpoch` + `acceptChunk` + `finishFile` + `complete(saved)`。
   **这两条路径都已有测试**，本卡只做装配，不重写。
