## 目标

实现「接收前知道要花多少空间、终检通过才算数据正确、导出提交之后才叫完成」这一条链路，
并把每个判断的依据做成**可解释的明细**而不是一个布尔值。

三件事都必须有可测试的实现，而不是靠 UI 层自觉：

1. **空间计划**：按卷核算暂存、导出峰值、源暂存、数据库估算与安全余量；
   查不到可用空间时返回 `unknown`，**不得**显示为「检查通过」。
2. **整文件终检**：全部 committed 后重新计算整文件摘要，一致才允许导出。
3. **导出与清理**：导出结果持久化后才展示完成；清理失败只影响空间回收，不把已导出文件改为失败。

## 范围内

- **空间计划模型**（纯 Dart，无平台依赖）：
  - 按实际存储卷/提供者**分别**核算；同一卷的并存需求相加，不同卷分别检查。
  - 明细项：未分配暂存、导出峰值额外占用、源文件必须暂存时的新增占用、数据库估算、安全余量。
  - `unknown` 是一等结果，与 `sufficient` / `insufficient` 并列。
  - 已实际分配的暂存空间不重复扣减。
- **终检**：对已 committed 的块按冻结清单重算整文件摘要；不一致时把不可信的块退回 `missing`。
- **导出**：安全文件名与冲突策略、导出记录持久化、失败可重试且不重复产出。
- **清理**：只清理任务授权范围内的暂存；**取消任务不得删除已成功导出的用户文件**。

## 接口与不变量

- **空间计划不能只返回布尔值。** `APP_AND_SERVICE_DESIGN.md` §8 明确要求每个卷给出解释性明细。
- **`unknown ≠ sufficient`。** provider 无法查询空间时必须返回 `unknown`，UI 必须让用户确认风险；
  内部任何分支都不得把 `unknown` 折叠成「通过」。
- **稀疏文件的逻辑长度不是已分配空间。** 现有占用必须由平台报告的实际分配字节提供；
  调用方不得用逻辑长度代替（接口命名与文档必须让这个错误难以犯下）。
- **安全余量是策略，不是保证。** `max(256 MiB, 预计新增占用 1%)`，按卷计算；
  它降低风险，不构成「空间足够」的证明（V2.1 §16.2）。
- **每个文件开始前与导出前都要重新检查。** 其他应用会继续占用空间，
  一次通过不授权后续所有写入。
- **完成＝终检通过且导出结果已提交。** 终检未通过不得进入导出；导出未提交不得显示完成。
- 清理失败**只**影响空间回收，不得把已导出文件改成失败（`APP_AND_SERVICE_DESIGN.md` §7）。

## 本次结果

### `t06-01-01`：空间计划

已实现 `space_plan.dart` 与 36 项测试（Flutter 测试总数 244 → 280；存储测试 81 → 117）。
详见[运行汇总](../testing/evidence/2026-09-20/t06-01-01/summary.md)。

模型逐条对应 V2.1 §16.2 与端侧设计 §8：按卷核算、五个明细项相加等于总需求、
已分配暂存不重复扣减、安全余量按卷取 `max(256 MiB, 1%)`。
最该保留的一条不变量是 **`unknown ≠ sufficient`**：判定先判空再比较，
不存在把缺失读数当作通过的路径，且提供的是 `permitsStartWithoutUserDecision` 这样的决策名而非布尔值。

**期间修正**：数据库估算常数由测试发现偏小——实测 200 块增长 53,248 B，
而初版常数估算 52,224 B（不足）。已提高到 320 B/块，并把测试加强为在两个块数上验证。
另外修正了三处文档不一致：`T01-02` 卡状态（实为已完成）、`T04-01` 卡状态（实为进行中）、
任务卡索引只列了 6 张卡中的 1 张。

### `t06-01-02`：整文件终检

已实现 `file_verification.dart` 与 22 项测试（Flutter 测试总数 280 → 302；存储测试 117 → 139）。
详见[运行汇总](../testing/evidence/2026-09-20/t06-01-02/summary.md)。

**一次流式读取同时回答两个问题**：整文件摘要（导出的闸门）与分块摘要（修哪一块）。
读两遍会让「经过用户收到的每一个字节」的路径 I/O 翻倍。字节以流消费、从不累积，
唯一增长的是 SHA-256 状态——缓冲整文件会违反 `AGENTS.md` §2 规则 4，在 20 GiB 上也会直接失败。

`wholeFileDigestMatches` 是 `bool?`：`null` 表示**没有计算**（有块缺失或损坏时，
摘要是在错误数据上算的，报 `false` 会暗示做过一次无法诚实进行的比较），
且 `null` 与 `false` 一样阻断导出。

损坏块被降级为 `missing`：协议 §5 允许 `committedBytes` 下降，理由正是一个内容错误的
committed 块会被之后每一次恢复信任。跨模块验证：终检降级后
`isFullyCommitted` 为假、`recordSavedExport` **自己**也拒绝——两个组件各自独立拒绝「假完成」，
都不需要相信对方的说法。

## 仍剩余（任务保持「进行中」）

1. **导出**：安全文件名与冲突策略、导出记录持久化、失败可重试且不重复产出。
2. **关闭终检与导出之间的缺口**：`recordSavedExport` 目前只检查 committed 块数、
   **不要求先通过终检**，所以「完成＝终检通过且导出已提交」只由调用约定保证。
   今天不可利用（转移引擎尚不存在、无生产调用方），但导出批次必须让**代码**而不是纪律来强制它。
3. **清理**：只清理任务授权范围内的暂存；取消任务不删除已导出的用户文件。
4. **接入检查时点与终检**：§8 的四个空间检查时点、以及「全部 committed 后调用终检」
   目前都没有任何调度代码在调用。
5. **按文件准入**：§16.1「空间不足时仅继续能证明空间足够的文件」需要滚动累加的调度，属 T05。
6. 平台 provider 的真实空间查询、真实暂存读取与真实卷标识（`FileSink`/`FileSource` 端口，属 B03/B04）。
7. 后台 isolate 划分（哈希是 CPU 密集的；调用方必须把大文件终检放到 UI isolate 之外）。

## 必做测试

覆盖 `QUALITY_AND_ACCEPTANCE.md` §3「存储与恢复」与 V2.1 §16.2：

| 场景 | 期望 |
| --- | --- |
| 0 B 文件 | 不产生暂存需求，仍在清单中 |
| 单文件、暂存与导出同卷 | 需求 = 暂存 + 导出副本 + 数据库 + 余量 |
| 单文件、暂存与导出不同卷 | 两卷分别核算，互不相加 |
| 已部分暂存 | 只计未分配部分，不重复扣减 |
| 可用空间不足 | `insufficient` 且给出缺口字节数 |
| 无法查询可用空间 | `unknown`，**不是** `sufficient` |
| 每次文件开始前重新检查 | 空间变化后结论随之变化 |
| 终检摘要一致 | 允许导出 |
| 终检摘要不一致 | 拒绝导出，坏块退回 `missing` |
| 终检时某块缺失 | `wholeFileDigestMatches` 为 `null`（未计算），仍阻断导出 |
| 坏块被降级后 | 文件不再「全部 committed」，导出守卫独立拒绝 |
| 导出失败 | 文件状态可重试，不报告完成 |
| 导出已提交 | 才允许完成 |
| 清理失败 | 已导出文件仍为成功 |
| 取消任务 | 已导出用户文件仍存在 |

**本任务使用纯 Dart 与临时文件系统**；平台 provider 的真实空间查询、真实 `syncData`
