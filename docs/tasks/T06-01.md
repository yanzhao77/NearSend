## 目标

实现「接收前知道要花多少空间、终检通过才算数据正确、导出提交之后才叫完成」这一条链路，
并把每个判断的依据做成**可解释的明细**而不是一个布尔值。

三件事都必须有可测试的实现，而不是靠 UI 层自觉：

1. **空间计划**：按卷核算暂存、导出峰值、源暂存、数据库估算与安全余量；
   查不到可用空间时返回 `unknown`，**不得**显示为「检查通过」。
2. **整文件终检**：全部 committed 后重新计算整文件摘要，一致才允许导出。
3. **导出与清理**：导出结果持久化后才展示完成；清理失败只影响空间回收，不把已导出文件改为失败。

## 范围内

- **空间计划模型**（纯 Dart，无平台依赖）：
  - 按实际存储卷/提供者**分别**核算；同一卷的并存需求相加，不同卷分别检查。
  - 明细项：未分配暂存、导出峰值额外占用、源文件必须暂存时的新增占用、数据库估算、安全余量。
  - `unknown` 是一等结果，与 `sufficient` / `insufficient` 并列。
  - 已实际分配的暂存空间不重复扣减。
- **终检**：对已 committed 的块按冻结清单重算整文件摘要；不一致时把不可信的块退回 `missing`。
- **导出**：安全文件名与冲突策略、导出记录持久化、失败可重试且不重复产出。
- **清理**：只清理任务授权范围内的暂存；**取消任务不得删除已成功导出的用户文件**。

## 接口与不变量

- **空间计划不能只返回布尔值。** `APP_AND_SERVICE_DESIGN.md` §8 明确要求每个卷给出解释性明细。
- **`unknown ≠ sufficient`。** provider 无法查询空间时必须返回 `unknown`，UI 必须让用户确认风险；
  内部任何分支都不得把 `unknown` 折叠成「通过」。
- **稀疏文件的逻辑长度不是已分配空间。** 现有占用必须由平台报告的实际分配字节提供；
  调用方不得用逻辑长度代替（接口命名与文档必须让这个错误难以犯下）。
- **安全余量是策略，不是保证。** `max(256 MiB, 预计新增占用 1%)`，按卷计算；
  它降低风险，不构成「空间足够」的证明（V2.1 §16.2）。
- **每个文件开始前与导出前都要重新检查。** 其他应用会继续占用空间，
  一次通过不授权后续所有写入。
- **完成＝终检通过且导出结果已提交。** 终检未通过不得进入导出；导出未提交不得显示完成。
- 清理失败**只**影响空间回收，不得把已导出文件改成失败（`APP_AND_SERVICE_DESIGN.md` §7）。

- [x] 安全余量按 `max(256 MiB, 预计新增占用 1%)` 逐卷计算，且被断言为策略值而非保证。

**期间修正**：数据库估算常数由测试发现偏小——实测 200 块增长 53,248 B，
而初版常数估算 52,224 B（不足）。已提高到 320 B/块，并把测试加强为在两个块数上验证。
另外修正了三处文档不一致：`T01-02` 卡状态（实为已完成）、`T04-01` 卡状态（实为进行中）、

### `t06-01-02`：整文件终检

已实现 `file_verification.dart` 与 22 项测试（Flutter 测试总数 280 → 302；存储测试 117 → 139）。
详见[运行汇总](../testing/evidence/2026-09-20/t06-01-02/summary.md)。

**一次流式读取同时回答两个问题**：整文件摘要（导出的闸门）与分块摘要（修哪一块）。
读两遍会让「经过用户收到的每一个字节」的路径 I/O 翻倍。字节以流消费、从不累积，
唯一增长的是 SHA-256 状态——缓冲整文件会违反 `AGENTS.md` §2 规则 4，在 20 GiB 上也会直接失败。

`wholeFileDigestMatches` 是 `bool?`：`null` 表示**没有计算**（有块缺失或损坏时，
摘要是在错误数据上算的，报 `false` 会暗示做过一次无法诚实进行的比较），
且 `null` 与 `false` 一样阻断导出。

损坏块被降级为 `missing`：协议 §5 允许 `committedBytes` 下降，理由正是一个内容错误的
committed 块会被之后每一次恢复信任。跨模块验证：终检降级后
`isFullyCommitted` 为假、`recordSavedExport` **自己**也拒绝——两个组件各自独立拒绝「假完成」，
都不需要相信对方的说法。

### `t06-01-03`：导出门禁与安全命名

已实现 `export_naming.dart` 与 26 项测试，并把 `recordSavedExport` 改为**必须**提供终检回执
（Flutter 测试总数 302 → 331；存储测试 139 → 168）。
详见[运行汇总](../testing/evidence/2026-09-20/t06-01-03/summary.md)。

**关闭了上一轮登记的缺口**：记录导出是产品告诉用户「文件安全了」的那一刻，
旧签名只检查块是否齐全、对「这些字节是不是对的字节」一言不发。
现在回执必须属于该文件、必须可导出、且覆盖的字节数必须等于该文件**当前**大小
（四次方的摘要说明不了已经变成八字节的文件）。

**测试也升级为真实回执**：`transfer_repository_test.dart` 不拼假回执，而是让暂存字节经
`_StagedMapReader` 真的跑一遍 `FileVerifier`，因此导出测试覆盖 `提交 → 终检 → 记录导出` 全链条。
新增门禁用例包括「所有块 committed 但整文件摘要不一致」——正是旧块数检查看不见的情况。

**安全命名**：为什么这里可以自动改名而 `relativePath` 不可以——后者参与清单摘要，
改写它就改了发送方签过名的字节；改名只改变副本落在哪里。默认按**大小写不敏感**处理，
因为两种错误不对称（多一个 `(1)` 无害 / 覆盖用户文件不可恢复）。
截断按 rune 而非 code unit（切进代理对会得到 U+FFFD，**与实际返回的名字不同**）；
截断撞上保留设备名（`CONSOLE` → `CON`）时加下划线前缀，并复用
`RelativePathRules.isReservedName` 以保持「保留名」只有一份定义。

**期间修正**：初版在截断留下尾随空格/点时**跳过整个文件**；写测试时意识到这会因为
截断产物而丢掉一个名字合法的用户文件，改为修剪。另有一处**测试前提写错**由测试自身暴露
（把 300 字节原名当作目标已有项比较——而策略先截断再比较，且 300 字节的段不可能存在于目标上）。

### `t06-01-04`：导出编排、清理与 schema v2

已实现 `export_service.dart`、schema v2 与 27 项测试（Flutter 测试总数 331 → 358；存储 168 → 195）。
详见[运行汇总](../testing/evidence/2026-09-20/t06-01-04/summary.md)。

**schema v2**：`exports` 增加 `saved_path`。落盘用的名字可能与冻结路径不同（命名策略会改名），
缺少它就无法回答「文件在哪」，也无法判断目标上的同名条目是不是自己上次写的。
`applyVersion1` **一个字都没改**——现场库已跑过它，改它会让新库与升级库产生无人察觉的差异。
**这也第一次让迁移框架有了真实升级路径可测**（1→2 端到端 6 项测试，含「新库与升级库列完全一致」）。
升级测试最初想用截断注册表造 v1 库，被 `assertWellFormed` **正确拒绝**；
改为直接调用 `applyVersion1` 重建 v1 状态，**没有为了让测试通过而放宽守卫**。

**顺序就是契约**：清点 → 命名 → 提交 → **记录** → 释放暂存。
假 sink 在 `deleteStaging` 被调用的**那一刻**检查数据库，断言导出记录已存在——
因为暂存是唯一还能产出用户文件的东西，在没有任何持久证据前释放它，一次崩溃就会留下
「既没有副本、也没有记录」。提交成功但记录失败时暂存**保留**；清理失败**不改变**导出结果。

**端口没有删除目标文件的能力**：`ExportSink` 只有 `inventory`/`commit`/`deleteStaging`，
不存在删除、移动或覆盖目标条目的方法。这比「记得不要调用」更强——
没有任何代码路径能做到，无论将来谁写编排。测试以操作序列钉住。

**「无法证明」的窗口**（V2.1 §15）：提交与记录之间副本已在目标但本地不知道。
能证明时关掉它——写之前先看自然名字下是否已有**摘要相同**的条目，有就复用而不是再写一份。
长度相同但摘要不同**不视为同一个**（同长度不是身份证明）；提供者读不到摘要时**按冲突处理**，
因为复用会谎报「导出成功」而那个文件可能根本不是用户的。**残余**：提供者给不出摘要时仍可能
多一个 `(1)` 副本，已登记入台账 §5。

**原子性报告而非声称**（V2.1 §15）：`commit` 返回 `atomic`，结果原样携带；
文档提供者做不到原子提交不是失败，但描述成原子就是假保证。未提交时为 `null` 而非 `false`。

## 仍剩余（任务保持「进行中」）

1. **平台 `ExportSink` 实现**：真实写入目标、真实原子重命名、真实枚举目标、真实删除暂存
   全部未实现（B03/B04 真机验证）。命名策略与编排目前输出的只是抽象结果。
2. **取消路径**：`takenPaths` 的完整性、取消流程本身均未实现；
   「不删除已导出文件」目前由端口能力缺失结构性保证，未经取消路径端到端验证。
3. **`takenPaths` 的完整性**：若调用方枚举不全，可能**覆盖用户已有文件**——
   这是本模块唯一会导致数据丢失的入口。端口实现必须明确：枚举失败时应拒绝导出并请用户处理，
   而不是当作「没有冲突」。
4. **回执可被应用内伪造**：Dart 无 friend class，`FileVerificationResult` 构造函数公开。
   本次关闭的是**遗漏路径**（开发者忘记先终检），不防御应用内恶意代码。后续可选：
   构造函数收为库私有并由 `FileVerifier` 唯一签发。
5. **旧的 `saved_path` 为 `NULL` 的导出记录**：「已保存到本目标」的分支会回退到冻结路径来报告位置，
   若那次导出其实改过名，这个回退就是错的。**需人工决定**是请用户确认位置还是接受近似。
6. **`inventory` 与 `commit` 之间的竞态**未处理；端口实现须在清点失败时拒绝导出而非重试到覆盖。
7. **`preserveStructure` 的目录创建**未实现也未测试，属端口职责。
8. **接入检查时点、终检与导出**：§8 的四个空间检查时点、以及「全部 committed 后终检 → 导出」
   目前都没有任何调度代码在调用。
9. **按文件准入**：§16.1「空间不足时仅继续能证明空间足够的文件」需要滚动累加的调度，属 T05。
10. 平台 provider 的真实空间查询、真实暂存读取、真实卷标识与真实文件系统行为（大小写、段长上限、保留名），属 B03/B04。
11. 后台 isolate 划分（哈希是 CPU 密集的；调用方必须把大文件终检放到 UI isolate 之外）。
