## 目标

把 T01-01 建立的一堆手工命令固化成**每次提交都会自动执行的门禁**：任何人（或 Agent）推送代码后，
格式化、静态分析、测试、协议固定向量、相对链接、敏感信息和两端构建都会在同一套流水线里跑一遍；
没有 Flutter 工程时必须记为未执行而不是假报通过。

同时补上行尾与二进制文件的显式策略，避免 Linux CI 与 Windows 工作区之间出现行尾误报。

## 范围内

- `.github/workflows/ci.yml`：
  - `repo-checks`：协议固定向量（`tooling/s0`）、Markdown 相对链接、敏感信息、依赖锁文件已跟踪。
  - `flutter-checks`：`flutter pub get` → `dart format` 校验 → `flutter analyze` → `flutter test`。
  - `build-android`：构建 APK（debug 与 release）。
  - `build-windows`：构建 Windows release。
- 固定 Flutter 版本并**校验下载包 SHA-256**，不使用未评估的第三方 Action 来安装 Flutter。
- `tooling/checks/` 下用 Python 标准库实现跨平台的相对链接检查与敏感信息检查（无第三方依赖）。
- `tooling/scripts/check.ps1` 增加这两项，使本地与 CI 检查一致。
- `.gitattributes`：明确文本行尾与二进制文件类型。
- 依赖锁定与版本追踪：校验 `pubspec.lock` 已被跟踪，并校验 CI 使用的 Flutter 版本与本地记录一致。
- 更新 `tooling/scripts/README.md` 与台账。

## 接口与不变量

- CI 的 Flutter 版本必须是**固定版本**，且下载包校验 SHA-256；不得使用 `latest`。
- CI 与本地使用同一组检查语义；`tooling/scripts/check.ps1` 与工作流不得出现两套规则。
- 检查失败必须让作业失败，不得使用 `continue-on-error` 掩盖。
- 密钥只存在于受保护环境，不进入工作流文件、日志或制品。
- 证据与制品只在必要时上传；不上传密钥、完整配对材料或用户文件。
- 新增 Action 必须记录用途、来源、维护状态与许可证（端侧设计 §12）。

### 首次 CI 失败及其修复（本任务的重要产出）

第一次运行有 3/4 作业通过，`Markdown relative links` 失败。它暴露了两件事：

1. `tooling/checks/README.md` 中用行内代码给出的链接语法示例被当成了真实链接 →
   检查器现在先移除代码围栏、行内代码与 HTML 注释。
2. **本地的「通过」只覆盖了 26 个 Markdown，而 CI 看到 29 个**，差额是当时尚未 `git add`
   的新文档 → 检查器现在会显式列出未跟踪的 Markdown 并打印 `NOT CHECKED`。

两者都已修复，并验证**真实坏链接仍会被抓到**，因此放宽没有削弱检查。
