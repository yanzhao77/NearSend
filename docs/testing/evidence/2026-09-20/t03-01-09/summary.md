## 2. 已有的世代检查为什么不够

存储层已经会拒绝「世代不是当前值」的提交，而且**在提交事务内再查一次**。
这让被取代的写入**无法提交**——但**没有**让它无法**写入**。剩下两个缺口都关于时间，而不是关于数据库：

1. **没有任何东西把同一文件的两个写入者串行化。** §8 的写入顺序把「文件锁」放在认证之后、
   写下任何字节之前。没有它，两个写入者会把各自的字节交错写进同一个暂存文件，
   而输的那一方在提交被拒时**字节早已落盘**——文件于是不再符合任何一方的意图。
   已提交的块行**仍然是对的**，这正是它危险的地方：数据库看起来没问题，
   而它描述的字节并不是赢家写下的字节。
2. **`revokeAndAdvanceLease` 只递增世代，不等待。** 一个正在 `writeVerifyAndSync` 中途的写入，
   在恢复流程分配下一代之后**会继续往新一代即将使用的那个文件里写**。
   §8 把「等待旧写入停止」放在「撤销旧会话」与「分配新 epoch」之间，正是为了让新一代
   从一个没有别人在动的文件开始。

## 3. 本类强制的顺序

```
拒绝旧世代的后续写入          （revokeAndDrain，立即）
等待它的写入者全部停止        （revokeAndDrain，被 await）
分配下一代                    （调用方，在仓库上）
校验已有数据                  （调用方）
```

**「先拒绝、再等待」是最容易写错的一步。** 如果只在世代变化时才拒绝，
那等待期间还会冒出新的旧世代写入，等待就永远不会结束。
测试固定了这两点：`accepts` 在 drain 完成**之前**就已为假，而 drain 在写入结束前不返回。

**排队的写入也要被计入等待。** 写入者在拿到文件槽**之前**就登记为 in-flight，
所以 drain 也会等一个还在排队的旧世代写入——它一到队首就会自我拒绝，
但「旧会话的工作已停止」必须包含「还堵在路上的那一份」。

**二次检查是必需的。** 一个写入可能先通过了检查、排在另一个写入之后，
等它排到队首时恢复已经接管。因此拿到文件槽之后**再查一次**，
不通过就抛 `STALE_LEASE` 且**一个字节都不写**。

## 4. 在途写入被允许做什么（以及为什么）

**它被允许写完，也允许它的提交成功。** 这是有意的：中止它只会留下一个半写的暂存文件，
没有任何好处；而 §8 的下一步「**校验已有数据**」正是让「旧世代下提交的块可以保留」
这件事安全的原因。栅栏保证的是写入**停止**，不是写入**被撤销**。

这一点在集成测试里被直接断言：旧世代写入在 drain 期间完成并 `committed`，
`committedChunkCount == 1`；随后才分配新一代。

## 5. 超时不得被读成「写入已停止」

`revokeAndDrain` 的 `timeout` 在到期时**抛异常**，而不是正常返回。
理由很具体：把超时当成「写入停了」的调用方，会在一个旧写入仍在往文件里写的时候分配新世代。
因此：

- 抛 `STALE_LEASE`，且**不分配**世代（集成测试断言 `leaseEpoch` 仍是旧值）；
- 世代**保持被撤销**，所以恢复可以重试，而期间不会再有旧世代的新工作开始。

## 6. 栅栏不是孤儿模块

上一批（`t03-01-08`）的窗口是一个「已实现但无人调用」的层，本批没有重复这一点：

- **仓库持有栅栏**（`ChunkRepository.fence`）。让每个调用方各造一个栅栏，等于有两个栅栏
  各自以为自己在仲裁同一个文件——那和没有栅栏是一样的。
- **`writeChunkWithFileLock`** 是「§8 写入顺序 + 文件锁」的一次调用；
  内层 `writeChunkThroughWindow` 刻意**不**持锁，以便锁本身能被单独测试。
- **`revokeAndAdvanceLeaseAfterWritesStop`** 把 §8 的三步做成一次调用，
  因为**顺序本身就是保证**：先递增世代会让在途写入继续写进新一代的文件。

## 9. 未执行与限制

1. **没有 HTTP 层**：栅栏与两个新方法**没有任何地方调用**。本次让「正确顺序」成为
   一次调用，但把它接到请求处理上仍需端点层。
2. **`writeChunkThroughWindow` 仍可被直接调用，从而绕过文件锁**。
   本层把持锁的路径做成**方便**的路径，而不是唯一路径。若要变成结构性保证，
   需要把内层方法私有化（会改动现有 14 项窗口测试的调用方式），属下一批的候选。
3. **栅栏是进程内的**。跨进程（同一个数据库被两个进程打开）没有仲裁。
   §8 的跨进程权威是已提交块行与 `lease_epoch`，而 SQLite 本身不提供文件锁语义给应用层；
   真正的多进程场景需要平台文件锁，未实现也未验证。
4. **`revokeAndDrain` 默认无限等待**。只有调用方传 `timeout` 才有上界。
   一个永不返回的 sink 会让恢复一直挂着——这是**已登记的产品决定**（§8 未给上界），
   不是遗漏。
5. **未做背压**：§9「接收端磁盘速度通过背压限制发送端」仍未实现。
6. **未做真实磁盘/真机验证**：所有存储写入使用假 sink；§8 的「每文件串行写入」
   在真实文件系统上的语义（同一文件的两个句柄、SAF/安全作用域资源的并发行为）未验证。
7. **未在 Android/iOS 真机运行**；本批为纯 Dart 存储层。

## 10. 需要人工重点复核的区域

- **文件锁的边界**：本类保证「同一 `fileId` 在本进程内一次只有一个写入者」。
  真实平台上「同一个文件」是否等于「同一个 `fileId`」需要复核——
  两个任务引用同一物理文件（例如用户把同一个目标目录用于两个任务）时，
  `fileId` 不同而文件相同，本层不仲裁。
- **允许在途写入提交**（见 §4）：这是读法。若协议要求「撤销后旧世代的提交一律失败」，
  则需要在 `commitPendingBatch` 里按世代拒绝对在途写入，本层要改成中止而非放行。
- **超时语义**（见 §5）：抛错且保持撤销状态。若产品要求「超时后强制接管」，
  那是一次安全性权衡，必须显式决定，不能顺手改。
- **`revokeAndDrain` 的无上界等待**（见 §9.4）。
- **栅栏与 `lease_epoch` 的双重检查**：两者都必须存在（前者管「新工作不开始」，
  后者管「提交不落地」）。若为简化去掉任一个，会留下本批描述的对应缺口。
