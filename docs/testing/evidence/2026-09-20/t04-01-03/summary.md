## 2. 核心保证：记录与效果在同一事务提交

`executeAtomically` 在一次事务内完成：读已有记录 → 执行效果 → 写入 completed 记录。
两个方向的分离都是有害的：

- **效果提交、记录丢失** → 重试会重复执行效果（块被写两次、状态机前进两次）；
- **记录提交、效果丢失** → 重试会重放一个从未发生的结果，等于告诉对端操作成功了。

测试直接验证了原子性，而不是只验证「返回值对」：效果会写入 `peers` 表中的一行标记，
然后断言

| 场景 | 标记行 | 记录 |
| --- | --- | --- |
| 效果成功 | 存在 | completed，含结果与 `lease_epoch` |
| 效果抛错 | **不存在**（随事务回滚） | **不存在**——没有幽灵 in-flight 记录 |

并且验证「效果抛错后的重试**确实重新执行**效果」——这是正确的，因为什么都没提交。

## 3. 并发：不需要 in-flight 窗口

重复请求会在 `BEGIN IMMEDIATE` 持有的写锁上等待，随后看到记录已 `completed` 并重放。
因此对原子操作而言**不存在可观察的 202 窗口，也不需要它**。
`beginInFlight`/`complete` 两阶段接口只保留给真正长时间的操作（如恢复），
因为 §9 明确要求那种情况返回 202。

测试覆盖：in-flight 时重复请求返回 `inFlight`；完成后返回 `replayed`。

## 4. 其他已验证行为

- **作用域**：同 request id 在不同 operation 或不同凭证指纹下是**不同**请求——
  §9 把作用域限定为「任务＋操作＋当前恢复凭证」，因此重新配对前后的同 ID 不应互相命中。
- **重启**：关闭并重新打开数据库后仍能重放，说明幂等不依赖内存状态。
- **保留期**：过期的 completed 记录会被清理，**in-flight 记录不会被清理**——
  删掉它会让效果被执行两次，正是幂等要防的事。
- **非法 request id**：在写入任何内容之前被拒绝（复用 T02-02 的规范 UUID 校验）。
