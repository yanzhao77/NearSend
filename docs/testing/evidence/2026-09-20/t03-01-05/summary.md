## 2. 页结构为什么是 sealed 类型

§6 规定「files 页**不得**带 fileId，chunks 页**必须**带 fileId」，而两种页的 items 是**不同记录**。
用一个类加一个可选字段，就允许 files 页带 fileId、chunks 页不带——
两件 §6 都禁止的事。sealed 类型让类型本身拒绝这两种组合，而不是靠构造时的检查。

页内的**索引不是自由的**：§6 说「每页覆盖连续索引区间」，
所以第 i 项的索引必须等于 `startIndex + i`。一条跳过或重复索引的页，
覆盖的字节集合与它声称的不一致。

## 3. 字节上限：测量，而不是估算

§6 的两项约束里，条目上限是人记得住的，**字节上限才是真正保护控制体的那条**。

分页器先按条目数贪心填充，然后**把候选页真的编码出来量一次**。
估算需要同时把 JSON 转义、十进制字符串字段和多字节字符都建模对，
而每次都对很难；把候选页编码出来量，在这些方面都无法出错。

### 一个诚实的发现：实践中条目上限总是先起作用

按 §5.1，路径上限是 **1024 UTF-8 字节**，所以一个文件条目最大约 1.3 KB，
128 条约 170 KB——远低于 1 MiB。块条目约 100 字节，1024 条约 100 KB。
**所以现实输入下字节上限永远不会触发，它是安全网。**

测试把这一点明确下来，而不是含糊带过：

- 用**最大合法路径**（341 个三字节字符 = 1023 字节）填满 128 项，
  断言**一页装得下**——说明条目上限才是那个起作用的约束；
- 用**发送方不可能构造出的**超大条目（60 万字节）驱动机制本身，
  断言页会在低于 128 项时收缩；
- 用**单个就超过 1 MiB** 的条目断言抛 `RESOURCE_LIMIT`，
  而不是在循环里打转。

## 4. 重传：由内容决定，而不是由区间决定

§6 的原话是「重传相同页返回成功，**重叠区间内容不一致**拒绝」——
它拒绝的是**内容不一致**的重叠区间，而不是任何重叠。
把规则写成「拒绝重叠区间」会拒绝一次只是换了分页边界的诚实重传。

**按索引存储是让第二条规则成立的结构**：「保存时按条目索引去重，不能用重复页增加累计数量」。
一条「把页 append 到列表」的实现能通过一个天真的重传测试，
却仍然会把重复的页算两次。有一条测试专门断言三次发送同一页后计数不变。

**乱序到达也能正确 seal**：§5 固定数组顺序为用户确认的逻辑顺序，
而页的 `startIndex` 正是承载该顺序的东西——所以按索引存、按升序读回，
即使页倒着到达也复现原数组（有测试）。

## 5. seal 的检查顺序：先解释，最后才是摘要

§6 列出「缺页、重复 fileId、块数量/长度错误、总摘要不一致」四种失败。
实现**按这个顺序检查**，摘要放在最后，理由是：
摘要对以上**每一种**问题都会失败，却对「是哪一种」一言不发。
先报「file index 1 is missing」比报「摘要不匹配」有用得多。

摘要检查是最强的一条，也是**让分片到达的清单等于发送方描述的那一份**的那条。
它复用 T02-01 已经写好的 `FrozenManifest.verifyDigest`
（T02-01 当初就在它的注释里写了「§6 seal」）。

块长度检查复用 `chunkLengthForIndex`：§5.3 从文件大小固定每块长度，
所以对端**不能**通过声明一个短块来跳过字节。

## 6. 30 分钟窗口：只回答问题，不执行清理

§6：「首次收到内容后 30 分钟 staging 未完成则清理并撤销该提议；不影响已经冻结的任务」。

本层提供 `isExpired(nowMillis)`，并在文档里写明：
**清理动作（释放暂存、撤销提议）不属于本层**，它属于拥有那些状态的服务端。
窗口从**首次收到内容**起算，而不是从提议开始——否则一个还没开始上传的提议
会在客户端仍在决定时过期。

## 8. 未执行与限制

1. **暂存是进程内的。** `ManifestStaging` 不持久化。服务端重启会丢失已收到的页，
   客户端需要重传——而重传是幂等且安全的（§6 的重传语义保证）。
   **但「staging 是否必须持久」是协议未说明的一点**，已登记待确认。
2. **没有端点逻辑**：本层不读请求、不做鉴权、不写响应。
   `PUT /transfers/{id}/manifest` 与 `POST /transfers/{id}/seal` 的实际处理未实现。
3. **没有 30 分钟窗口的执行者**：`isExpired` 只是一个谓词，没有任何代码在调用它，
   也没有任何代码执行「清理并撤销提议」。
4. **没有把页交给 `SpacePlan`**：接收确认前要按冻结后的清单做空间检查，
   这一步尚未接线。
5. **§3 的 `transfers` 创建与 staging 生命周期**（`POST /transfers` → STAGING → seal →
   WAITING_ACCEPT）未实现；本层只覆盖 seal 之前的部分。
6. 未在 Android/iOS 真机运行。

## 9. 需要人工重点复核的区域

- **暂存是否需要持久化**（见 §8.1）：本层选择内存，理由是重启后重传是安全的。
  若协议要求 staging 跨重启保留，则需要一个持久化设计。
- **`isExpired` 的调用方尚未存在**：一个只被测试调用的谓词不会让任何东西过期。
  接线时必须确保有人定期检查它，且清理动作**不**影响已冻结的任务。
- **seal 的检查顺序是实现的读法**：§6 列出四种失败但未规定顺序。
  当前顺序是为了错误信息更有用；若对端按特定错误码处理，需重新确认。
- **`seal()` 的幂等性**：本层让第二次 `seal()` 返回同一份清单而不报错。
  §6 说「seal 后页不可修改」但没说重复 seal 的语义，§9 的 `requestId` 幂等另论。
- **空清单可以 seal**：`files` 为空时 `_assertNoGaps` 会拒绝（「no file page has been
  received」），但**单个 0 字节文件**是合法的（0 块），有测试覆盖。
  若产品要求至少一个文件，需要显式的计数检查。
