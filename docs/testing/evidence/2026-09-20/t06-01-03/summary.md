## 2. 关闭上一轮登记的缺口

上一轮登记：「`recordSavedExport` 只检查 committed 块数，**不要求先通过终检**，
所以『完成＝终检通过且导出已提交』只由调用约定保证」。

本次把 `verification` 改成**必填参数**，缺口由代码关闭：

```dart
ExportRecord recordSavedExport({
  required String fileId,
  required String targetUri,
  required FileVerificationResult verification,   // 新增，必填
});
```

记录导出的那一刻就是产品告诉用户「你的文件安全了」的那一刻。旧签名只检查块是否齐全，
对「这些字节是不是对的字节」一言不发——而正是这一点决定用户拿到的是不是原文件。

新增的三道检查：

1. **回执必须属于这个文件**——拿别的文件的回执证明不了这次导出；
2. **回执必须可导出**——有块缺失/损坏或整文件摘要不一致时拒绝；
3. **回执覆盖的字节数必须等于该文件当前的大小**——四次方的摘要说明不了现在已经是八字节的文件，
   所以文件被重新注册后旧回执自动失效。

第 3 条是刻意的：它让回执带上「关于哪个版本的哪份数据」的约束，而不只是一张通行证。

### 这项强制**不**证明什么（重要）

Dart 没有 friend class，`FileVerificationResult` 有公开构造函数，因此**应用内**的调用方
原则上可以自己拼一个 `isExportable == true` 的对象。本次关闭的是**遗漏路径**——
开发者写导出步骤时忘记先终检——这才是真实风险；它并不防御应用内部的恶意代码
（能那样做的代码同样可以直接调 `markChunksMissing`）。

已在 §9 登记为复核项，并给出后续选择：把回执的构造函数收为库私有 + 由 `FileVerifier` 唯一签发，
或引入只能在库内构造的回执类型。

### 测试一并升级为真实回执

`transfer_repository_test.dart` 原来直接调用 `recordSavedExport`。本次没有给它拼一个假回执，
而是让它**真的跑一遍终检**：暂存字节被记录在一个 map 里，由 `_StagedMapReader` 提供给
`FileVerifier`。导出测试因此覆盖了 `提交 → 终检 → 记录导出` 的完整链条，
而不是只覆盖最后一步。新增的门禁用例：

| 用例 | 断言 |
| --- | --- |
| 所有块 committed 但整文件摘要不一致 | 拒绝——**这正是旧的块数检查看不见的情况**：字节都在，但都是错的 |
| 用 A 文件的回执去记录 B 文件 | 拒绝 |
| 回执取得后文件被替换（大小变化） | 拒绝，因为「四次方的摘要说明不了八字节的文件」 |

## 3. 安全命名：为什么这里可以改名，而 `relativePath` 不行

`RelativePathRules.validate` 判断一条**到达**的路径能否接受，且**故意原样返回**——
那个字符串参与清单摘要，改写它就改了发送方签过名的字节。

`export_naming.dart` 做的是另一件事：给一条已被接受的路径，产出一个**落盘用的名字**并解决冲突。
所以「自动重命名」在这里是允许的：「`UI_UX_SPEC.md` §4 要求冲突策略（询问/自动重命名/跳过；
MVP 默认自动安全重命名）」，而改名只改变副本落在哪里，不改变发送方签了什么。
导出记录保留冻结路径原样，另存实际使用的目标。

### 默认按大小写不敏感处理

Windows、macOS 与 Android 常用的 exFAT 卡都会把 `Photo.JPG` 与 `photo.jpg` 解析到同一个条目。
两种错误的代价**不对称**：

- 把大小写敏感的目标当成不敏感 → 多一个 `(1)` 后缀，无害；
- 反过来 → **覆盖用户已经有的文件**，不可恢复。

所以默认 `targetIsCaseInsensitive: true`，需要时可以显式关掉。

### 截断必须走 rune，不能走 code unit

一个段超出上限时截断。若按 code unit 截断，可能切进代理对，留下一个孤立代理——
它不是合法 UTF-8，写往文件系统时会被替换成 U+FFFD，
**结果是一个与实际返回的名字不同的名字**。实现按 rune 长度累加，测试用 4 字节 emoji
并断言 `utf8.decode(utf8.encode(segment)) == segment`。

### 截断可能撞上保留设备名

把 `CONSOLE` 截到 3 字节就是 `CON`——在 Windows 上它解析到设备，
文件看起来保存成功却根本不存在。实现检测截断**之后**的名字并加下划线前缀；
检测取决于「保留名」的定义，因此把 `RelativePathRules.isReservedName` 公开复用，
而不是在导出层再抄一份列表——两份列表一定会漂移，而漂移的那份恰恰没人测。

### 截断留下的尾随空格/点：修剪，而不是放弃文件

初版实现在结果以空格或点结尾时返回「跳过」。写测试时意识到这不对：
用户那个文件的名字是合法的，**因为截断产物而丢掉整个文件**比名字短一点更糟。
改为修剪尾随空格与点，再在必要时回退到 `fallback-stem`。
（`a path segment must not end with a space or a dot` 是协议自己的规则，
所以这里不能只是容忍。）

### 一处测试前提写错（由测试自己暴露）

「加了后缀仍然不超长」这条用例最初把**原始 300 字节名字**放进 `taken`，
结果策略没有产生后缀而失败。检查后确认**是测试错了**：策略先按上限截断再比较冲突，
而 300 字节的段**不可能**存在于目标上（目标文件系统本身就限长）。
改为先取一次截断后的名字、再把它作为已存在项——这才是真实场景（同一文件的第二次导出）。

## 5. 未执行与限制

1. **没有导出编排，也没有清理。** 端侧设计 §7 要求的顺序——
   「导出成功记录持久化**后再**清理暂存」以及「清理失败只影响空间回收，不把已导出文件改为失败」——
   **本次未实现**。本次只做了「记录导出前必须通过终检」这一半。
2. **没有 `FileSink` 端口实现。** 命名策略输出的是相对路径；真正写入目标、
   原子提交、删除暂存都需要平台端口，本次未定义。
3. **`takenPaths` 由调用方提供。** 平台无法枚举目标已有条目时，**可能覆盖用户文件**——
   这是本模块唯一会导致数据丢失的入口，见 §6。
4. **命名策略未接入任何调用方。** 与空间计划、终检一样，实现完整但无人调用。
5. 未在 Android/iOS 真机运行；未验证任何真实文件系统的大小写行为、长度上限或保留名规则。
   大小写与长度上限的默认值是**保守选择**，不是实测结论。

## 6. 需要人工重点复核的区域

- **`takenPaths` 的完整性。** 若调用方给不全（平台无法枚举、枚举有竞态），
  策略会认为名字空闲并覆盖用户已有的文件。「默认大小写不敏感」只降低了概率，没有消除它。
  平台端口实现时必须明确：枚举失败时应**拒绝导出并请用户处理**，而不是当作「没有冲突」。
- **回执的可伪造性**（见 §2 末）。已登记，等待导出批次一并定案。
- **`ExportTargetLayout.preserveStructure` 会创建目录。** 目录创建本身未被测试，
  也不属于命名策略；端口实现需要决定目录创建失败（权限、只读卷）时的语义。
- **`maxSegmentBytes` 默认 200** 是对 255 字节上限的保守选择，
  但部分文件系统（如某些 Android 提供者）限制更严；需要真机确认。
- **`_isAcceptable` 依赖协议校验器。** 若将来协议放宽/收紧路径规则，
  导出命名会随之变化——这是复用同一份定义的好处，但也意味着协议的改动会波及导出。
