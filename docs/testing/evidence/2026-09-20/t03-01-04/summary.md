## 2. §7 的开篇规则：ID 参数必须先解析校验

§7 的第一句就是：

> 所有 ID 参数须先解析校验。

所以路由匹配**在校验之后才返回**：`ApiRoutes.match` 把 `{id}`/`{fid}` 按 §4 的规范小写 UUID 校验、
把 `{index}` 按 §4 的十进制字符串校验，任何一项不合格就直接拒绝。
业务逻辑**拿不到**未校验的参数——它拿到的是一个类型化的 `MatchedApiRequest`。

19 行被建模为**数据**而不是手写的字符串比较链，所以「表被改动」这件事可以被测试发现：

- 表中每个 `方法 + 模板` 必须在注册表里（新增/删除/改方法都会失败）；
- 没有两条路由冲突；
- 每条路径都在 §7 的 `/v1` 前缀下；
- `HttpMethod` 只有 `get`/`post`/`put` 三个值——表里没用的方法没有定义的行为，
  所以也不存在「正确回答它」的方式。

## 3. 百分号编码在**整个请求目标**中被拒绝

这个 surface 携带的每一个值都是**未转义的规范形式**：规范 UUID、协议十进制字符串、
固定词，或本服务端产出的不透明游标。所以正确的请求从不需要转义，
而拒绝转义在到达匹配器之前就去掉了一整类绕过：

- `%2F` 解码成分隔符会**改变路径的段数**；
- `%2e%2e` 解码成 `..` 会把一个字面量变成**穿越**。

检查作用在**原始目标**上，所以无论 HTTP 层是否已经解码都成立。

**对游标的推论值得点名**：§7 说游标是「返回的不透明值」却没定格式，
所以本读法要求服务端签发的游标**不含需要转义的字符**。
这是对草案留白处的一个约束，已登记入台账 §5 待确认。

## 4. 未知方法答 `NOT_FOUND`（一个需要确认的解读）

§11 的表里**没有 405**，而 `AGENTS.md` §3 禁止发明协议细节。
保守的读法是 §7 已经写下的那条：「任务查询对无权限资源统一 404」。
这也顺带**不确认哪些端点是存在的**。

这是一个**解读**而不是规格的直述，已登记入台账 §5 待协议冻结前确认。

## 5. 块偏移是推导的，不是传入的

§8：「块索引从 URL 十进制解析，offset = index × 4194304，**乘法先检查范围，
不能接受客户端任意 offset**」。

`chunkOffsetBytes` 只从索引与文件大小推导；**没有任何查询参数**能让一个 offset 进来——
有一条测试直接断言 `?offset=100` 被拒（该参数不在允许集合里）。
另有测试覆盖：索引超出文件块数被拒、0 字节文件没有第 0 块。

## 6. 分页上限与 §6 的 kind/fileId 配对

| 端点 | 上限 |
| --- | --- |
| `GET .../manifest?kind=files` | 128（§6 文件页） |
| `GET .../manifest?kind=chunks` | 1024（§6 块页） |
| `GET .../status` | 1024（§9 每页最多 1024 区间） |
| 其他 | 不接受 `limit` |

manifest 的上限**取决于 kind**，所以该路由在 `kind` 缺失时**拒绝**而不是猜一个默认值。

§6 的另一句「files 页不得带 fileId，chunks 页必须带 fileId」也在 `manifestKind()` 里强制：
一个 kind 与 fileId 互相矛盾的页，是两种实现会读成不同意思的页。

未知查询参数被拒绝（与 §4 拒绝未定义 JSON 字段同理）：
**一个实现遵守、另一个实现丢弃的参数，是任何一方的测试都抓不到的行为差异**。

## 7. 期间由测试发现的两个缺陷

**其一：路由模板的前导空段。** `template.split('/')` 对 `/v1/offers` 得到
`['', 'v1', 'offers']`，而请求路径切出的是 `['v1','offers']`——
两者形状不同，于是**每条路由都匹配失败**（15 项测试同时报 NOT_FOUND）。
修正为 `sublist(1)`，让模板与请求路径**形状一致**，匹配成为逐段比较而不是两套约定的比较。

**其二：kind 相关上限的哨兵值落穿。** 初版在 `kind=files` 时返回了哨兵值 `-1`
（本该是 128），测试直接读到 `Actual: <-1>`。修正为显式区分两种 kind，并在 `kind` 缺失时拒绝。

两个都是**测试先发现、而不是审阅先发现**的——这正是把「表」和「上限」写成可断言数据的理由。

## 9. 未执行与限制

1. **没有 HTTP 服务器或客户端**：没有连接处理、没有 TLS、没有请求体读取、没有响应写出。
   本层只做「这个方法＋路径是不是一个已知端点、它的参数是否合法」。
2. **没有鉴权决定**：§7 区分「除 pair 外均需要有效 Bearer」（`BearerHeader` 已实现解析，
   但**没有任何地方调用它**）、`taskResumeSecret` 专用请求体、受限完成查询令牌。
3. **没有任何端点逻辑**：19 条路由都能匹配，但没有一条在做 §7 描述的事。
4. **请求体与响应体未建模**（除 `PairRequest`/`PairResponse`）：`POST /transfers`、
   分页体、`/checkpoint`、`/complete` 等的字段都还没定义。
5. **§6 的页结构 `{manifestDigest,kind,fileId?,startIndex,items}` 未建模**；
   「重传相同页返回成功、重叠区间内容不一致拒绝、按索引去重」也未实现。
6. **§8 的块头规则**（单一 `Content-Length`、拒绝 `Transfer-Encoding`、不许压缩等）仍未实现。
7. 未在 Android/iOS 真机运行。

## 10. 需要人工重点复核的区域

- **未知方法的 404 解读**（见 §4）：需在协议冻结前确认是采用 404，
  还是为 405 单独定义语义（那将是一次协议增补）。
- **游标必须免转义**（见 §3）：这是对 §7 留白格式的约束。若将来允许含 `%` 的游标，
  本层的整目标拒绝就必须放宽为「路径段拒绝、查询值允许」——那是一次安全性权衡，不应顺手改。
- **`startIndex`/`limit` 的必填性**：§7 只给出参数名，没说哪些必填。
  本读法是 `kind` 必填、`startIndex` 默认 0、`limit` 默认为该端点上限。**需确认**。
- **`limit` 未做「1 MiB 同时约束」的计算**：§6 要求页「同时受 1 MiB 上限约束」，
  即条目数上限之外还有字节上限。本层只做条目数上限；字节数取决于条目的实际大小，
  属响应构建阶段，**实现响应时必须补上**。
- **`fileId` 在 `status` 路由上的必填性未定**：§7 写作 `?fileId=...&startIndex=...&limit=...`，
  但状态分页也可能只查任务级状态。本层允许它缺省，**需确认**。
