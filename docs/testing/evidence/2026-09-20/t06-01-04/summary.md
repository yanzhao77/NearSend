## 2. 为什么需要 schema v2

导出记录原先只有 `target_uri`。但**落盘时用的名字可能与冻结路径不同**——
命名策略会为了不覆盖用户已有文件而改名。缺少这个名字有两个直接后果：

- 无法回答「我的文件在哪」；
- 重试时无法判断「目标上那个同名条目是不是我自己上次写的」。

这两件事都不能靠冻结路径代替，所以 `exports` 增加 `saved_path`，`currentVersion` 升到 2。

**这也第一次让迁移框架有了真实的升级路径可测。** T04-01 一直登记着
「目前只有 schema v1；多版本迁移待 v2 出现后端到端验证」——现在 v2 出现了，
新增 6 项升级测试：达到当前版本、旧行保留、旧导出行的名字是 `NULL` 而不是编造的冻结路径、
升级前写了一致性备份且备份可读、升级后可以写入名字、
以及**新库与升级库的列完全一致**（后者是防止「改 v1 建表语句」这类漂移的关键断言）。

**`applyVersion1` 一个字都没改**：现场数据库已经跑过它，改它会让新库和升级库产生
没有任何测试会察觉的差异。v2 用 `ALTER TABLE ... ADD COLUMN`，SQLite 中它是事务性的，
且保留每一行。

### 升级测试期间的一个发现

需要用 `StorageMigrator` 造一个 v1 库来测升级。最初的做法是把注册表截断到 v1，
但框架**正确地拒绝**了：

```text
NS-STORAGE-002: the registered steps reach version 1 but the schema constant is 2
```

`assertWellFormed` 要求注册表恰好达到 `currentVersion`——这对**出厂**注册表是正确的守卫。
所以测试改为**直接调用 `applyVersion1` 并写入元数据行**，重建 v1 构建当时留下的状态。
**没有为了让测试通过而放宽守卫**：那等于拿一个真实的保护换测试便利。

## 3. 导出编排：顺序就是契约

端侧设计 §7：

> 导出使用安全文件名策略、冲突策略和尽可能原子的目标提交；**导出成功记录持久化后再清理暂存**。
> **若清理失败只影响空间回收，不把已导出文件改为失败。**

实现的顺序是：清理目标清点 → 命名 → 提交 → **记录** → 释放暂存。两条性质被测试钉住：

| 性质 | 测试 |
| --- | --- |
| 记录先于释放 | 假 sink 在 `deleteStaging` 被调用的**那一刻**检查数据库，断言导出记录已经存在 |
| 记录失败则暂存保留 | 提交成功但记录被拒 → `failed`、`wroteToTarget` 为真、暂存 `retained`、**没有调用删除** |
| 清理失败不改变结果 | `deleteStaging` 抛错 → `isSaved` 仍为真、`stagingRelease` 为 `failed`、`cleanupFailure` 有值 |
| 提交失败则什么都不释放 | `failed`、暂存 `retained`、无删除调用 |

理由很直接：**暂存是唯一还能产出用户文件的东西**。在没有任何持久证据表明用户已拿到副本之前
释放它，一次崩溃就会留下「既没有副本、也没有记录」。

## 4. 端口**没有**删除目标文件的能力

`ExportSink` 只有三个方法：`inventory`、`commit`、`deleteStaging`。
**不存在删除、移动或覆盖目标条目的方法可以调用。**

`AGENTS.md` §5 与 V2.1 §16.1 都要求取消任务不得删除已导出的用户文件，V2.1 还要求
删除已保存文件必须是**独立明确**的操作。把能力从端口里拿掉，比「记得不要调用」更强：
没有任何代码路径能做到这件事，无论将来谁写编排。

测试以操作序列钉住这一点，断言一次成功导出只产生
`inventory → commit:<name> → deleteStaging`。

## 5. 「无法证明」的窗口，以及本次能关掉多少

V2.1 §15：「对无法证明导出提交结果的后端，**重启后检查已有目标或请用户确认，不盲目新建重复文件**。」

提交写入目标与写入导出记录之间存在一个窗口：副本已经在目标上，但本地没有任何东西知道。
本次在**能证明时**关掉它：写之前先找「自然名字」下是否已有条目，若其 **摘要**与冻结摘要相同，
就复用它而不是再写一份，然后记录。

| 情况 | 行为 |
| --- | --- |
| 目标条目摘要与冻结摘要相同 | 复用，不写出第二份；记录指向它 |
| 摘要相同但长度不同 | 不视为同一个（长度也参与判定） |
| 长度相同、摘要不同 | **不视为我们写的**——同长度不是身份证明，按冲突处理（自动改名） |
| 提供者读不到摘要 | **无法证明**，按冲突处理，**不盲目复用** |

最后一行是刻意的：复用会报告「导出成功」而那个文件可能根本不是用户的文件。
宁可多一个 `(1)` 副本，也不能谎报。

**残余**：「不盲目新建重复文件」在提供者无法给出摘要时仍可能产生一个 `(1)` 副本。
缓解手段是导出记录检查（已记录就不再写）与 `NameConflictPolicy.ask`（可让用户确认）。
已登记入台账 §5。

## 6. 原子性：报告，而不是声称

V2.1 §15：「仅在同一可控文件系统且支持该操作时使用原子重命名……**不能伪称原子操作**。」

`ExportSink.commit` 返回 `ExportCommitResult.atomic`，`ExportOutcome.committedAtomically` 原样携带。
文档提供者做不到原子提交**不是失败**，但把它描述成原子就是给用户一个假保证。
没有任何提交时该字段为 `null`——不是 `false`，因为那时没有可描述的对象。

## 9. 需要人工重点复核的区域

- **`saved_path` 为 `NULL` 的旧记录。** v1 写的导出记录没有名字。
  目前 `existingExport` 会返回 `savedPath == null`，而「已保存到本目标」的分支会回退到
  **冻结路径**来报告位置——如果那次导出其实改过名，这个回退就是错的。
  **需要人工决定**：是请用户确认位置，还是接受这个近似。
- **复用判定只信摘要。** 若提供者给出的摘要是「元数据里记的」而非重新计算，
  复用判定就建立在不可靠输入上。端口实现必须说明摘要来源。
- **`recordSavedExport` 的保存路径与提交路径必须一致。** 目前由编排顺序保证（同一个变量），
  但没有类型层面的约束；若将来有人在提交后重新命名，记录会指向不存在的名字。
- **端口能力缺失是唯一的「不误删」保证。** 一旦有人给 `ExportSink` 加上删除目标的方法，
  该保证立刻消失。复核时应把这个缺失当作**设计要求**而不是遗漏。
