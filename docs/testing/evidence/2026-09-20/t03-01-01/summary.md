## 2. 把「先比对再发令牌」做成结构性保证

§2 的原话是：

> 采用每连接隔离的信任上下文；**必须在发送令牌、HTTP 请求及文件内容之前完成指纹比对**。
> 即使证书受系统 CA 信任也必须比对 pin，不能只在"不可信证书回调"中比对。

这类规则的问题不是难写，而是**写错了也不报错**：一个先发令牌、后比对指纹的实现，
对着诚实的服务端照样工作，所有功能测试照样通过。

所以令牌在这里不是一个字段：

```dart
/// Refuses until the certificate has been compared and matched.
String get pairingToken { ... }   // 未比对 → ProtocolViolation(PAIR_REJECTED)
```

调用方**没有顺序需要记住**——在比对成功之前，令牌根本无法取得。

配套的三条不变量：

| 不变量 | 依据 |
| --- | --- |
| 比对失败**关闭**连接，不得在同一上下文上重新协商 | §2「比较失败关闭连接」；在对端身份校验已失败的连接上重试，正是重试循环变成攻击的方式 |
| **每连接隔离**：一个连接的失败不泄漏到另一个 | §2「采用每连接隔离的信任上下文」 |
| **除非比对显式返回 trusted，否则关闭** | 本次收紧：连「证书编码不可用」也关闭。不变量越简单越不容易被绕过，而且失败后连接状态不需要调用方再推理 |

最后一条是本次在实现中主动收紧的：初版在「无法计算的证书编码」时抛异常但**不关闭**上下文。
虽然那条路径只有我们自己的 TLS 层可能触发，但保留一个「失败后仍可继续协商」的状态
本身就是不必要的风险面，所以改为统一关闭。

## 3. 指纹的三种写法，形状相同、语义不同

§2 把 pin 定义为 `SHA-256(服务端叶证书完整 DER)`，并明确**不是** PEM 文本摘要、
**不是**公钥 SPKI 摘要。弄错会得到一个**看起来完全合理、但永远匹配不上**的 pin——
或者更糟，匹配上错误的东西。

因此：

- `serverFingerprintOf(List<int> leafCertificateDer)` 的参数类型是**字节**，
  没有任何接受 PEM 字符串的重载，传错是**编译错误**；
- 测试直接断言 `serverFingerprintOf(der) != sha256(utf8.encode(pemText))`；
- 另一个测试断言对 DER **一部分**求摘要与对整体求摘要不同（覆盖 SPKI 类错误）。

### 为什么比较不是常数时间

指纹发布在用户正在扫描的二维码里，**它不是秘密**，因此比较上的时序信道不泄漏任何
攻击者尚未拥有的信息。手写一个常数时间比较等于为不存在的问题发明密码学代码，
`AGENTS.md` §5 明确禁止。这一点写在代码注释里，避免后来者「顺手加固」。

## 4. QR 载荷：严格解析，因为它是第一个不受信输入

载荷决定「连到哪里」和「信任谁」。§4 要求未定义字段**拒绝**而非忽略，实现按此处理。

拒绝的情况（每一项都有独立测试）：

| 类别 | 被拒绝的输入 |
| --- | --- |
| 结构 | 非 JSON、JSON 数组、纯文本、URL（§3 规定二维码是 JSON，不是会自动跳转的东西） |
| 大小 | UTF-8 超过 4096 字节——**在解析之前**检查，超大载荷不会被解析 |
| 字段 | 顶层多余字段、candidate 内多余字段（如夹带 `path`） |
| `kind` / 版本 | `kind` 不是 `lft-pair`、缺失 `kind`、版本写成字符串或布尔、版本为负 |
| 指纹 | 63/65 位、**大写**、非 hex、base64 形状（长度正确） |
| `sessionId` | 大写、去掉连字符、非 UUID |
| 令牌 | 带 `=` 填充、长度不符、非规范写法、标准 base64 字母表（`+`/`/`）、空串 |
| 候选地址 | 空列表、超过 8 个、端口 0 / 65536、端口写成字符串、非对象元素 |
| `host` | 带 scheme、带凭证（`user:pass@`）、带路径、带查询、带空白、带方括号；IPv4 越界与前置零；主机名；IPv6 双省略、组超 4 位 |
| 过期 | 0、写成字符串 |

### 两个值得单独说明的判定

**大写指纹被拒绝。** §2 固定为小写十六进制。大小写不敏感地接受会让同一个指纹有两种拼写，
而它被用于**相等比较**——正是最不该有两种拼写的地方。

**IPv4 前置零被拒绝。** `10.0.0.01` 在某些解析器里按八进制解释，于是一个字符串可能意味着两个地址。
拒绝比解释更安全。

**方括号地址被拒绝。** 端口是独立字段，不需要方括号消歧；同时接受两种写法等于给同一个地址两个名字。
编码端由本项目控制，按裸地址输出。这一条已在任务卡与本文档写明，因为它是**有意的严格**而非疏漏。

## 5. base64url：为什么专门写一个解码器

§4 要求「解码后重新编码必须相同」。无填充 base64 的末位字符含有空闲比特，
因此**多个不同字符串可以解码到同一批字节**。一个被当作凭证使用的值，正是最不该出现
「同一个令牌有两种拼写」的地方。

实现先做字母表与填充检查，再解码，再**重新编码比对**，任一不符即拒绝。
测试用一个非规范的等长写法验证它被拒绝。

## 8. 需要人工重点复核的区域

- **iOS 的二维码扫描与相册权限**、Android 的相机权限与「本地网络」权限：
  本次未涉及任何平台权限路径，真机实现时必须单独复核。
- **`expiresInSeconds` 只是提示**（§3 明确以服务端状态为准）。当前实现只校验它为正数，
  **不**把它当过期时间。后续实现令牌生命周期时不得改成信任它。
- **候选地址的信任语义**：§3 说候选选择不能绕过 pin。当前实现只保证「拿到令牌必须先比对」，
  但**选哪个候选**由调用方决定；后续网络层必须确保无论选哪个候选，pin 都来自二维码本身，
  而不是来自连接结果。
- **`abandon()` 的调用时机**：用户取消、超时、切换候选都要调用它，否则上下文保持半开状态。
  目前没有调度代码，因此这一条尚无端到端验证。
- **比较不是常数时间**是有意选择（见 §3）；若将来有人要求改为常数时间，
  应先说明威胁模型变化，而不是默认「加固」。
