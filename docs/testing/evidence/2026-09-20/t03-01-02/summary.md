## 2. 令牌生命周期：三条被测试钉住的规则

| §3 的要求 | 实现与验证 |
| --- | --- |
| 300 秒内单次消费 | 消费后立即移除；第二次尝试为 `unknownSession` |
| **以服务端单调计时判定** | 注入的是「单调流逝毫秒」，测试用同一起点验证「差 1 毫秒仍有效、到点即失效」 |
| 服务重启时未消费令牌全部失效 | **不持久化任何令牌状态**，因此重启失效是**构造性**的，而不是一个可能被漏掉的失效步骤；测试用一个新 issuer 验证旧令牌不可用 |
| 配对响应丢失时不恢复已消费令牌 | 没有任何 API 能把已消费的令牌放回去；测试先消费、再重试、再重新 `issue` 一个新令牌 |
| 失败统一 `PAIR_REJECTED` | 见 §3 |

**「以单调计时判定」为什么重要**：墙上时钟可以被 NTP 校正或用户改时间向后移动，
那会延长一个令牌的寿命或让一个活着的令牌立刻过期。所以类型名就叫
`typedef MonotonicMillis = int Function()`，并在文档里说明它**必须**是单调的。

## 3. 只保存令牌的摘要（并说明一个没有测试的性质）

§2 已经确立了这条原则：「服务端仅保存恢复密钥验证摘要」。配对令牌适用同样的处理：
issuer 只保存 `SHA-256(令牌的规范拼写)`，比较也在摘要上进行。
这样一次进程内存转储拿不到可用的令牌。

**诚实说明**：这是一条**代码层面的性质，没有测试覆盖**——Dart 的无反射能力
（Flutter 不提供 `dart:mirrors`）意味着测试无法断言「内部字段里没有原令牌」。
它由代码结构保证（字段类型是 `_OutstandingToken{digest, expiresAtMillis}`，
没有任何地方保存原值），并在此处明确标注为**未经测试**，而不是含糊带过。

## 4. 比较**不**声称常数时间——以及为什么

比较秘密通常应当常数时间，但 Dart **不提供这种保证**：JIT 可以重排，
运行时对普通比较不给出时序契约。在这种情况下手写一个「常数时间」循环会是一种
**虚假保证**——它断言了平台并不提供的性质，比普通比较更糟。

真正约束风险的是结构性的东西：

- **256 位熵**（32 随机字节，`Random.secure()`），且 §3 明确「限流不替代随机熵」；
- **单次消费**；
- **300 秒窗口**；
- **滑动失败限流**（每来源 5 次/分钟，全局 30 次/分钟）；
- **只比较摘要**，原令牌不在内存里。

这条推理写在代码注释里，避免后来者「顺手加固」而引入一个不成立的保证。

## 5. 统一失败做成结构性：本地理由够不到线上答案

§3 要求「失败统一 `PAIR_REJECTED`，避免暴露令牌存在性」。
未知会话、令牌错误、已过期三种原因在线上必须**无法区分**。

实现同时保留了两者，并让它们不可能混淆：

```dart
enum PairingRejection { unknownSession, expired, wrongToken }   // 仅本地诊断

ProtocolErrorCode? get wireCode {
  ...
  case PairingAttemptResult.rejected:
    return ProtocolErrorCode.pairRejected;   // 常量，理由改变不了它
}
```

测试断言三种拒绝原因**映射到同一个** `wireCode`，同时断言本地理由仍然可区分
（诊断需要它），并单独断言 `rejection` 字段从 `wireCode` 不可达。

## 6. 限流检查在令牌之前

`consume` 的**第一步**是限流，然后才看令牌。这一顺序有实际意义：
一个已被限流的调用方，即使这次拿的是**正确**令牌，也只会得到 `RATE_LIMITED`，
因此它无法通过「换一个令牌再试」来判断哪个令牌存在。

测试直接覆盖这一点（`a valid token is still refused while the source is limited`）。

其余限流行为：每来源与全局两个滑动窗口；来源之间互不影响；
失败会随时间移出窗口（不是永久锁定）；**一次成功不清除失败记录**——
§3 数的是「窗口内的失败次数」，中间成功一次不改变之前试过什么。

## 7. `/v1/pair` 模型：两处刻意的克制

### 客户端标签按 **UTF-8 字节**计量，不是字符

§3 限 128 字节。测试用 `'é'`（2 字节）证明差异：64 个恰好通过，65 个被拒绝——
按字符计数会让多字节标签突破 §3 实际设定的上限。
本次为此在 `protocol_validation.dart` 增加了 `utf8BytesOf`，让「按字节计量」只有一处实现。

### capability 词表**不发明**

§3 把响应写成 `capabilities:[...]` 却一个标识符都没枚举。`AGENTS.md` §3 禁止以偏好
定下未解决的协议细节，所以这里**复用 T02-02 的 `CapabilitySet`**（只实现有界值类型，
不含词表），而不是另造一套。测试全程使用合成标识符，并有一条测试专门断言
「空列表是合法答案」——因为没有词表时，空列表不能被这一层拒绝。

## 8. 期间发现的一个协议内在张力（未修，已登记）

§9 规定 `requestId` 幂等：「每次操作持久化请求摘要和结果」。
但 §3 规定「配对响应丢失时**不恢复**已消费配对令牌，重新生成 QR」。

也就是说，**配对是 requestId 幂等的一个例外**：同一个 `pairToken` 的响应丢失后，
重试同一请求**不应该**重放成功结果（令牌已消费），而应让用户重新扫码。
本层只校验了 `requestId` 的规范 UUID 格式，**没有**实现任何幂等重放语义——
因为对配对而言，重放正是 §3 禁止的事。

这一张力属协议层，需人工确认：是明确把配对排除在 §9 的幂等范围之外，
还是为配对定义「同一 requestId 返回同一拒绝」的语义。**已登记入台账 §5。**

## 10. 未执行与限制

1. **没有 HTTP 传输层**：`POST /v1/pair` 的实际请求/响应、状态码映射、
   以及 §7 的线上错误体 `{code, message, retryable, requestId?}` 序列化**未实现**。
   本层只产出 `ProtocolErrorCode`（已含 `wireCode`/`httpStatus`/`retryable`）。
2. **没有会话访问令牌的签发与交付**：`accessToken` 由调用方提供；
   `Authorization: Bearer`、恢复凭证与 receipt 交付（§3）未实现。
3. **没有限流的状态持久化**：限流是进程内的，重启后清零。
   §3 没有要求持久化，但真机实现时需要确认这一读法。
4. **`Random.secure()` 未在真机验证**：未确认它在 Android/Windows 上确实来自平台 CSPRNG。
5. **没有真实 TLS 引擎，也没有网络绑定（B02 阻塞）**；本层不做任何可达性判断。
6. **没有任何生产调用方**：issuer、请求模型与信任上下文都实现完整但没有调度。

## 11. 需要人工重点复核的区域

- **「只保存摘要」没有测试覆盖**（见 §3）。复核时应以代码审查确认，而不是依赖测试绿灯。
- **§9 幂等与 §3 不恢复令牌的张力**（见 §8）：需在协议冻结前定案。
- **成功不清除失败记录**是有意选择（§3 数的是窗口内失败次数）。
  若产品上认为「成功即证明是合法用户」，这是一个需要显式决定的产品/安全权衡。
- **限流只是纵深防御**：§3 明确「限流不替代随机熵」，因此
  `generatePairingTokenBytes` 的熵**不得**因为有限流而下调。
- **`expiresInSeconds` 在请求/响应两侧的权威性**：响应里的 1800 秒是服务端声明的有效期，
  客户端可以据此提前续期，但**不得**把它当作「过期后仍可用」的依据。
- **clientLabel 是展示用**：§3 明确它不是身份。目前只做长度与控制字符检查；
  若 UI 将来对它做任何格式化（例如 Markdown），必须先按不可信输入处理。
