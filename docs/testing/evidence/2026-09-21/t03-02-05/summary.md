## 2. 三个问题与答案

### 2.1 Android 的 `X509Certificate.der` 是否给出与 Windows 相同的摘要？

**是。** 二维码里的 pin 由 **Windows** 生成证书时算出；Android 侧由自己的 TLS 栈对
`certificate.der` 再算一次。测试断言
**Android 每一次呈现的指纹都等于二维码里的 pin**，在真机上通过。

这才是这条链路里最容易悄悄出错的地方：若两个平台对 DER 的理解不同，pin 会在一边匹配、
在另一边永远匹配不上，而**桌面上的全部测试仍然全绿**。断言写在
`integration_test/android_lan_pairing_test.dart`，用的是与扫码器同一个严格解析器解析载荷，
没有任何桩。

### 2.2 `badCertificateCallback` 在 Android 上的调用时机是否与 Windows 一致？

**一致。** 正确 pin 的用例断言回调**确实被调用过**（否则我们的比较根本不存在）；
错误 pin 的用例断言回调被查询过、且**它看到的就是真实证书**，连接随后被拒——即 Android
上同样是「我们的比较拒绝的」，而不是别的东西拒绝的。

### 2.3 应用能否真的经 Wi-Fi 到达这台 Windows？

**能。** 配对返回 `200`，随后用返回的会话令牌创建传输返回 `201` 且 `state=STAGING`。
这两个响应只可能来自真实服务端的真实端点。

## 3. 期间发现并修正的真实缺陷：release 构建没有网络

`flutter create` 只在 **debug** 与 **profile** 清单里放 `INTERNET` 权限，主清单没有。
后果是 **release 构建完全无法联网**——而联网正是这个产品的全部意义。**任何 debug 模式的
测试都看不见这个缺陷**，它会一直潜伏到第一次 release 安装。

已把权限加进 `android/app/src/main/AndroidManifest.xml`，并在注释里写明它为什么属于主清单。
注意这会让平台目录相对 `flutter create` 原始输出产生一处**非标识类差异**，T01-01 的
平台目录审计在下次复跑时应把它作为**有意的产品必需改动**接受，而不是当成业务逻辑混入。

## 4. 环境前提是条件，不是给定

本运行开始时，上一台真机 `22081283C` 在构建途中掉线，随后接入的是 `25102RKBEC`。
新设备**Wi-Fi 处于关闭状态**，走的是蜂窝数据（`rmnet_data3`），到 `192.168.10.100` 的
路由被送到了运营商网关——**首轮测试因此不可能成功，与服务端和代码都无关**。

启用 Wi-Fi 后它自动连上 `CMCC-pbD4` 并取得 `192.168.10.4/24`，随后一切正常。
记录这一条是因为它印证了台账 B01/B02 的立场：**「同一局域网」是一项必须每次确认的前提**，
不是配好一次就永远成立的东西。

## 5. 未取到的证据（如实说明）

测试隔离区（isolate）的 `stdout` **不会**被转发到 `flutter test` 的控制台，而设备自身的
logcat 被启动器的 `flutter` 标签刷满，因此**两个指纹的具体字符串没有进入日志**。
本运行不声称有这一项证据。

替代它的是断言本身：`presentations.every((p) => p == payload.serverFingerprint)`
在真机上通过，即「Android 算出的每一个指纹都等于 Windows 公布的 pin」。
**断言比打印更强**——打印出来的值可以是错的，被校验过的不会。测试源码已入库，可复核。
